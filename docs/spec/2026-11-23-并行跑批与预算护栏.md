# 规格 S-004：并行跑批 · 预算与成本护栏

> 状态：已实现
> 日期：2026-11-23
> 影响范围：`python_backend/api/routers/evaluation.py`、`python_backend/modules/evaluation/analysis.py`、`python_backend/modules/evaluation/test_parallel_budget.py`、`frontend/src/modules/evaluation/AgentEvalPanel.vue`、`frontend/src/HarnessApp.vue`

## 1. 背景与目标

S-002 / S-003 把测评从「比对文本」升级到「断言过程」，也有了多轮、稳定性、出处与门禁。但它仍然是**串行**跑的：`for case in cases` 逐个执行，样本量一上来，等待时间线性增长，而单次通过率又因为样本太少而没有统计意义。对照高星项目（Inspect AI、SWE-bench、AgentBench 都并行跑任务），这是当前评测能力的规模瓶颈。

同时没有任何**预算护栏**：一次跑批可能烧掉大量模型额度，用户只能事后看 `avgTokens`。评测平台必须能在烧钱前设上限。

本规格做两件事：

1. **样本级并行跑批**：并发度可配，样本之间互不影响（一个样本炸了不拖垮整轮）。
2. **预算与成本护栏**：token 预算、样本数上限与运行时限，超了就不再领新样本，已跑的样本照常出结果，未跑的样本明确标记为「已跳过」。

## 2. 非目标

- **不改执行引擎与 Worker 协议**。并发只发生在测评层（同时发起多个样本的执行），执行队列与 Worker 语义不变。
- **不做容器沙箱**。隔离仍只有 `eval:` 命名空间一层；副作用工具的限制留到后续规格。
- **不做 USD 预算**。成本只做估算展示，预算上限用 token、样本数与秒数表达。
- **不引入外部评测框架**。

## 3. 数据模型变更

无表结构变更。新增字段都落在已有的 `summary`（JSON）里：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `concurrency` | int | 本轮并发度 |
| `budgetTokens` | int | token 预算上限，0 表示不限 |
| `budgetSeconds` | int | 运行时限（秒），0 表示不限 |
| `budgetSamples` | int | 样本数上限，0 表示不限 |
| `tokensUsed` | int | 本轮实际消耗的 token 合计 |
| `budgetExhausted` | bool | 是否因预算或时限提前收工 |
| `skippedCount` | int | 因预算/时限未执行的样本数 |
| `estimatedCostUsd` | float | 估算成本；未给单价时为 0 |

`evaluation_result.verdict` 新增取值 `skipped`（配合 `failure_kind = "budget_exhausted"`），表示该样本因预算/时限未执行。

## 4. 接口契约

### 4.1 发起测评

`POST /evaluation/runs` 请求体在原有字段之外增加：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `concurrency` | int | 1 | 并发度，取值 1–16；1 表示沿用串行 |
| `budgetTokens` | int | 0 | token 预算上限，0 表示不限 |
| `budgetSeconds` | int | 0 | 运行时限（秒），0 表示不限 |
| `budgetSamples` | int | 0 | 样本数上限，0 表示不限 |
| `pricePerMTok` | float | 0 | 每百万 token 的美元单价；0 表示不估算成本 |

### 4.2 汇总

`run.summary` 增加上表中的 `concurrency`、`budgetTokens`、`budgetSeconds`、`budgetSamples`、`tokensUsed`、`budgetExhausted`、`skippedCount`、`estimatedCostUsd`。

- `passRate` 的分母改为「实际执行并评分的结果数」= `resultCount - skippedCount`；没有样本被跳过时与原口径完全一致。
- `passAtK` 与 `flakyRate` 不统计被跳过的样本（它们没参与评估，不该拉低稳定性指标）。

### 4.3 门禁指标

`analysis.GATE_METRICS` 增加 `tokensUsed` 与 `skippedCount`，Harness「评测配置」的门禁指标下拉同步这两项。

## 5. 行为约定

### 5.1 并行执行

- 并发单位是**样本 × epoch**。同一 `case_id` 的不同 epoch 视为不同任务，可并发。
- 任务由固定大小的线程池领取（默认 1，最大 16），**结果落库始终在主线程按任务顺序进行**，避免并发写测评库。
- 单个样本抛异常只影响该样本：记 `verdict=failed`、`failure_kind=unknown`，其余样本照常执行。
- `concurrency=1` 时行为与改造前完全一致（回归口径）。
- **并发不等于提速**：执行仍受 Worker 容量限制。本机 Worker 容量为 1 时，多个样本只是排队执行，总时长不变；提速需要多个 Worker 实例。并发度的真实价值是把「提交」与「执行」解耦，并让多 Worker 场景自动吃满容量。

### 5.2 预算护栏

- 三种上限：token 预算、样本数上限、运行时限。任一触发即不再领取新任务。
- 预算在**领取下一个任务之前**检查；已被领取的任务会跑完（不中断正在跑的样本），因此实际消耗可能略微超过上限一个样本的量。
- 被跳过的样本写入一条 `verdict=skipped` 的结果，`failure_kind=budget_exhausted`，`detail` 说明是哪种上限触发。
- 预算触发后整轮**不算失败**，运行状态仍是 `completed`；`summary.budgetExhausted=true`、`skippedCount>0` 供门禁与页面判断。
- **token 计量只覆盖产生 usage 事件的执行**：需求澄清门闸这类「模型判定后提前返回」的路径不发 usage 事件，token 记 0。核心澄清场景因此依赖**样本数上限**与**时限**兜底，而不是 token 预算。

### 5.3 成本估算

- `estimatedCostUsd = tokensUsed / 1_000_000 * pricePerMTok`。
- 未给单价（0）时估算值为 0，页面显示「—」而不是 $0.00，避免误读为「免费」。

## 6. 验收标准

- [x] `concurrency=1` 时单测结果与改造前一致（结果顺序、判定、口径）。
- [x] 多样本并发执行时总耗时接近「单样本耗时 × 批数 / 并发度」，明显小于串行。
- [x] 并发下结果列表顺序按数据集样本顺序稳定。
- [x] 某个样本执行抛异常时，其它样本照常出结果。
- [x] token 预算触发后，剩余样本记 `skipped`，`summary.skippedCount` 与 `budgetExhausted` 为真，`passRate` 分母排除 skipped。
- [x] 运行时限触发时行为同上。
- [x] 样本数上限触发时行为同上。
- [x] `tokensUsed` 等于本轮所有已执行样本的 token 合计。
- [x] 被跳过的样本不拉低 `passAtK` / `flakyRate`。
- [x] 门禁可用 `tokensUsed` 与 `skippedCount` 判定。
- [x] 页面能填并发度与三种预算，跑批后能看到预算消耗、跳过数量与跳过原因。

## 8. 已知限制与后续

- **并发受 Worker 容量限制**：单 Worker 时并发只是流水线，不提速。
- **预算是软上限**：正在跑的样本不打断，实际消耗可能超出上限一个样本。
- **token 计量有缺口**：不产生 usage 事件的执行（澄清门闸提前返回）记 0 token，token 预算对这类场景无效，需用样本数上限或时限兜底。要补齐得改执行链路的 usage 上报，属于另一件事。
- **没有 USD 预算**：单价要用户自己填。
- **没有沙箱**：并发跑批仍会调真实模型、真实工具，副作用仍在（留待后续规格）。
