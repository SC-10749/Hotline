# 规格 S-002：Agent 测评增强（轨迹断言 · 重复稳定性 · 运行出处 · 失败分类）

> 状态：已实现
> 日期：2026-11-23
> 影响范围：`python_backend/modules/evaluation/`、`python_backend/infrastructure/evaluation_store.py`、`python_backend/api/routers/evaluation.py`、`frontend/src/modules/evaluation/AgentEvalPanel.vue`、`frontend/src/api.js`、`frontend/src/HarnessApp.vue`

## 1. 背景与目标

现有测评只能回答「这句话答对了没有」：样本只有一条 `input`，跑批只执行一次，评分只看最终文本，`collect_output` 把 `type=text` 的事件拼起来就当答案。这套口径测不出四件事：

1. **过程对不对**。技能没调、工具报错、澄清轮次不对，最终文本写得再漂亮也判 passed。
2. **稳不稳**。同一份测评集连跑两次 passRate 不一样，无法区分「改动让 Agent 变好」与「随机波动」。
3. **能不能复现**。运行记录里的 `version` 是手填字符串、默认空；快照只存 name/type/description/case_count，不存样本正文。事后无法回答「上周那轮 78% 是在什么配置下跑出来的」。
4. **失败在哪**。`verdict=failed` 不区分是意图判错、技能缺失还是工具炸了，60% 的通过率没有可执行的诊断。

本次改动在**不新增依赖、不新建数据表、不改 Harness 菜单分组**的前提下，把这四件事补上。

目标产出：

- 样本可以声明**轨迹断言**（该调什么技能、澄清几轮、工具错误上限）。
- 一轮测评可以**重复多次**，产出 passAtK 与 flakyRate。
- 每轮运行自动记录**出处**（模型、技能包 sha、代码 commit、测评集版本）。
- 每个失败样本带**失败分类**。
- 以上四个能力在 Harness「测评中心」下有一个**页签**能看、能跑、能查轨迹。

## 2. 非目标

- **不做多轮对话 / 用户模拟器**。样本仍是单条 `input`；需求助手的多轮澄清质量暂不纳入本规格。
- **不做样本级沙箱隔离**。测评仍打真实后端与真实记忆库，隔离问题单独立项。
- **不做容器化 / 分布式评测**。单机串行跑批维持现状。
- **不引入 Inspect AI / promptfoo 等外部框架**，也不新增 pip / npm 依赖。
- **不发布对外排行榜**，不做人工基线。
- **不改发布治理（release）模块的门禁**。本次的 `/evaluation/gates/check` 是评测自检门禁，与发布门禁是两套东西。

## 3. 数据模型变更

只给已有表加列，不建新表。SQLite 迁移沿用 `EvaluationStore._initialize` 里既有的 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 写法。

### evaluation_run

| 列 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `epochs` | INTEGER | 1 | 本轮每个样本重复执行次数 |
| `provenance` | TEXT | '' | JSON 字符串，见 §4.4 |

### evaluation_result

| 列 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `epoch` | INTEGER | 0 | 第几次重复，从 0 起 |
| `failure_kind` | TEXT | '' | 失败分类，空串表示不适用 |
| `exec_run_id` | TEXT | '' | 本次样本对应的执行运行编号，用于回查轨迹 |
| `trace` | TEXT | '{}' | JSON 字符串，轨迹摘要（不含事件明细） |

### evaluation_snapshot

`payload` JSON 增加两个键，其余保持原样：

- `cases`：`[{case_id, input_text, expected_output, rubric}]`，即快照时刻的**样本正文**（可复现的最小前提）。
- `sha256`：对 `cases` 规范化 JSON 取 sha256，用于校验快照未被改动。

## 4. 接口契约

### 4.1 发起测评

`POST /evaluation/runs`

请求体新增一个字段，其余不变：

```json
{ "datasetId": "dataset-xxx", "agent": "chat", "version": "", "epochs": 3 }
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `datasetId` | string | 是 | — | 测评集编号 |
| `agent` | string | 否 | 默认 `chat` | 本轮使用的助手类型 |
| `version` | string | 否 | 默认 '' | 手工标注版本，保留兼容 |
| `epochs` | integer | 否 | 1 ≤ epochs ≤ 10，默认 1 | 每个样本重复次数 |

响应结构不变：`{ run, results, message }`。

### 4.2 运行详情与汇总

`GET /evaluation/runs/{eval_run_id}` → `{ run, results }`

`run.summary` 在原有四个字段之外增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `resultCount` | int | 结果条数（= 样本数 × epochs） |
| `epochs` | int | 本轮重复次数 |
| `passAtK` | float | 每个样本的 epochs 次**全部通过**的样本占比 |
| `flakyRate` | float | 同一样本在不同 epoch 判定不一致的样本占比 |
| `avgLatencyMs` | float | 单次执行平均耗时（毫秒） |
| `avgTokens` | float | 单次执行平均 token 数 |
| `failureKinds` | object | 失败分类 → 条数，如 `{"tool_error": 2}` |

`passRate` 语义**不变**：通过条数 / 结果条数。epochs=1 时与改造前完全一致。

`results[]` 每条新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `epoch` | int | 第几次重复 |
| `failure_kind` | string | 失败分类，空串表示不适用 |
| `exec_run_id` | string | 执行运行编号 |
| `trace` | object | 轨迹摘要：`{agent, counts, tools, tokens, latencyMs}`，无轨迹时为 null |

### 4.3 轨迹查询

`GET /evaluation/runs/{eval_run_id}/trace?caseId=<case_id>&epoch=<epoch>`

`epoch` 省略时取 0。响应：

```json
{ "trace": {
  "caseId": "case-xxx", "epoch": 0, "agent": "skills",
  "counts": {"clarify": 2, "tool_start": 5, "tool_end": 5, "tool_error": 0, "usage": 1, "step": 3, "text": 4},
  "tools": ["retrieval"],
  "tokens": 1234, "latencyMs": 3200,
  "events": [{"event_id": 1, "created_at": "2026-11-23T10:00:00", "type": "tool_start", "level": "info", "tool": "retrieval", "summary": "调用检索工具"}]
} }
```

| 情形 | 响应 |
| --- | --- |
| 测评运行不存在 | 404「测评运行不存在」 |
| 样本或 epoch 在本轮不存在 | 404「测评样本不存在」 |
| 正常 | 200，上述结构 |

事件最多返回 500 条，超出按 `event_id` 升序截断（保留最早的 500 条）。

### 4.4 运行出处

`run.provenance` 是 JSON 字符串，字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `datasetId` | string | 测评集编号 |
| `datasetVersion` | int | 发起时刻测评集的版本号 |
| `caseCount` | int | 样本数 |
| `agent` | string | 助手类型 |
| `epochs` | int | 重复次数 |
| `model` | string | 模型名（来自 `settings.model_name`） |
| `commit` | string | git commit，仓库不可用时为空串 |
| `skills` | object | 技能名 → SKILL.md 的 sha256 前 12 位 |
| `createdAt` | string | ISO 时间 |

`skills` 取仓库 `skills/*/SKILL.md`（不取 `data/skills/` 安装副本），保证出处随代码走。

### 4.5 门禁检查

`POST /evaluation/gates/check`

请求：`{ "target": "<eval_run_id>", "base": "<eval_run_id>" }`（`base` 可选）

响应：

```json
{ "passed": true,
  "checks": [{"label": "通过率", "metric": "passRate", "op": ">=", "value": 0.85, "actual": 0.91, "passed": true}],
  "config": {"dimensions": [], "gates": []} }
```

门禁条目取自 `evaluation_config.gates`，每项形如 `{"label", "metric", "op", "value"}`：

| `metric` | 含义 |
| --- | --- |
| `passRate` | 通过率 |
| `passAtK` | 全对率 |
| `flakyRate` | 不稳定率 |
| `avgLatencyMs` | 平均耗时 |
| `avgTokens` | 平均 token 数 |
| `avgTurns` | 平均对话轮数（S-003 增加） |
| `failedCount` | 失败条数 |
| `caseCount` | 样本数 |
| `passedCount` | 通过条数 |
| `resultCount` | 结果条数 |

不在表内的指标一律判「指标或比较算子不支持」即未通过；页面「评测配置」的下拉与这张表保持一致。

| `op` | 含义 |
| --- | --- |
| `>=` `<=` `>` `<` `==` | 比较算子 |

判定规则：取 `target` 运行的 summary 字段；**字段缺失视为该条不通过**（`actual` 为 null），不当作 0；`base` 存在时同时返回 `base` 的实际值到 `actualBase`，供页面展示差值。

### 4.6 导出

`GET /evaluation/runs/{eval_run_id}/export?format=csv|json` 保持原路径。CSV 表头在原六列后追加 `epoch`、`failure_kind`、`latency_ms`、`tokens` 四列；JSON 结构不变（`run`、`results` 已含新字段）。

## 5. 行为约定

### 5.1 轨迹断言（rubric type = trace）

样本 rubric 支持新类型 `trace`：

```json
{ "type": "trace", "expect": {
  "agent": "skills",
  "minClarify": 1, "maxClarify": 3,
  "expectTools": ["retrieval"], "forbidTools": ["shell"],
  "maxToolErrors": 0, "minSteps": 2 } }
```

| 键 | 类型 | 语义 |
| --- | --- | --- |
| `agent` | string | 本轮实际助手类型必须相同 |
| `minClarify` / `maxClarify` | int | 澄清事件次数的闭区间 |
| `expectTools` | string[] | 列出的工具每个都必须出现 |
| `forbidTools` | string[] | 列出的工具一个都不能出现 |
| `maxToolErrors` | int | 工具错误数上限 |
| `minSteps` | int | step 事件数下限 |

判定规则：

- `expect` 缺失或为空 → `verdict=invalid_rubric`。
- `expect` 含未知键 → `verdict=invalid_rubric`，detail 指名未知键（不静默忽略）。
- 轨迹不可用（无事件） → `verdict=not_scored`，detail「轨迹不可用，未评分」，**不判失败也不判通过**。
- 全部条件满足 → `verdict=passed`，score 1.0。
- 任一条件不满足 → `verdict=failed`，score 0.0，detail 列出**所有**不满足的条件。

### 5.2 复合规则（rubric type = multi）

`{ "type": "multi", "mode": "all" | "any", "rules": [ ...rubric... ] }`

- `mode=all`：全部子规则通过才算通过；`mode=any`：任一子规则通过即通过。
- score 恒为子规则分数的算术平均。
- 缺 `rules`、`rules` 为空或 `mode` 非法 → `invalid_rubric`。
- 子规则可以是任意已支持类型（含 `multi` 与 `trace`），递归深度上限 5，超出记 `invalid_rubric`。

### 5.3 重复执行与稳定性

- 一个样本的 epochs 次执行互相独立，`conversation_id` 为 `eval:<运行编号>:<样本编号>:<epoch>`，互不串扰。
- 仍**串行**执行，不引入并发。
- `passAtK` = 全部 epoch 都判 passed 的样本数 / 样本数；epochs=1 时等于 passRate。
- `flakyRate` = 同一样本各 epoch 的 verdict 不一致的样本数 / 样本数；epochs=1 时恒为 0。
- 样本在某个 epoch 执行失败（异常/超时）时，该 epoch 的 verdict 为 `failed`/`timeout`，仍计入分母。

### 5.4 失败分类

`failure_kind` 取值与判定顺序：

1. `timeout` —— verdict 为 timeout。
2. `judge_unavailable` —— verdict 为 scorer_unavailable。
3. `tool_error` —— 轨迹里 `tool_error > 0`。
4. rubric 显式声明的 `failureKind`（如 `{"type":"contains","value":"x","failureKind":"wrong_intent"}`）——内容类失败的自述假设。
5. `unknown` —— 其余情况。

**约束**：内容类失败（意图错、技能缺失、幻觉）**不做自动猜测**。自动判定只能区分超时、判分器不可用、工具报错这三类有客观证据的情况，其余一律 `unknown`，需要靠 rubric 显式声明或人工看轨迹。

### 5.5 隔离与并发

- 本次不引入样本级沙箱。测评请求的 `conversation_id` 带 `eval:` 前缀，与真实会话命名空间区分。
- `epochs` 的多次执行之间不共享会话上下文。
- 跑批仍在后台线程执行，`GET /evaluation/runs/{id}` 轮询进度。

## 8. 已知限制与后续

- **样本仍无沙箱**：测评会写入真实会话与记忆；本规格只做命名空间区分，不解决污染问题。
- **无多轮能力**：需求助手的多轮澄清质量仍测不了，需另立规格（用户模拟器 + 轮次断言）。
- **failure_kind 大多为 unknown**：自动分类只覆盖三类有证据的失败；要提高诊断力，需人工标注样本或引入 LLM 分类器（另议）。
- **flakyRate 需要样本量**：样本少于 10 条时 flakyRate 统计意义很弱，页面展示时需带样本量。
- **快照体积**：存样本正文会让快照变大，测评集上限 500 条时可接受，再大需另设归档策略。
