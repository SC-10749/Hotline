# 规格 S-003：多轮评测 · 用户模拟器 · 门禁 CLI · Harness 测评页清理

> 状态：已实现
> 日期：2026-11-23
> 影响范围：`python_backend/modules/evaluation/`、`python_backend/infrastructure/evaluation_store.py`、`python_backend/api/routers/evaluation.py`、`python_backend/modules/storage/relational.py`、`python_backend/eval_gate.py`、`frontend/src/HarnessApp.vue`、`frontend/src/api.js`、`frontend/src/modules/evaluation/AgentEvalPanel.vue`

## 1. 背景与目标

S-002 把评测从「比对最终文本」升级到「断言过程」，但仍有两处硬缺口，外加 Harness 测评页本身的毛病：

1. **多轮测不了**。样本只有一条 `input`，跑一次就结束。需求助手的核心能力恰恰是**多轮澄清**——助手问、用户答、再问、再答。现在这条链路完全在评测之外。
2. **用户模拟器没有**。真实对话里用户不会一次把需求说完，往往中途改口、只肯先说一半。没有模拟用户，就没法造出「助手问对了但用户只答了一半」这种场景。
3. **测评会话污染用户侧栏**。跑批的会话编号是 `eval:<运行>:<样本>:<轮次>`，写进了 `ai_session`，而 `session_list` 没有过滤，用户侧栏会冒出一堆「eval:xxx」会话。
4. **门禁只能手改接口**。`evaluation_config.gates` 页面读得到、改不了；CI 里也没有能跑的判定入口。
5. **Harness 测评页有假面板**：测评总览的「能力维度」每行进度条写死 `width:0%`、分数恒为 `—`；同一页又出现发布门禁与评测自检门禁两套口径；「评测配置」页改不了门禁。

本规格一次性收口这五件事。

## 2. 非目标

- **不做真正的沙箱**。测评仍在真实 Worker 上跑，隔离只到「`eval:` 命名空间 + 会话列表不展示」这一层，不引入容器或独立数据库。
- **不做助手侧的对话质量评分**。模型评分规则沿用现有 `type=model`，本规格只增加过程类断言。
- **不改发布治理模块**。发布门禁仍是发布治理的事，本规格的门禁是评测自检。
- **不删 demo 模式的演示数据**。技能/工具/模型/Agent/工作空间未连接时的演示数据是产品有意保留的引导态。

## 3. 数据模型变更

### evaluation_case（加两列）

| 列 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `turns` | TEXT | '[]' | JSON 数组，用户在首轮之后的每一句话 |
| `user_profile` | TEXT | '' | 模拟用户画像；非空且没有 `turns` 时由模型扮演用户 |

两列都通过 `ALTER TABLE ADD COLUMN` 迁移，老库自动补齐。

### evaluation_run / evaluation_result

无表结构变更。新增字段都在已有的 `summary`（JSON）与 `trace`（JSON）里：
- `summary.avgTurns`：平均对话轮数。
- `trace.turns`：本样本的总轮数；`trace.transcript`：助手逐轮输出数组；`trace.counts.turns`：轮数计数（供轨迹断言使用）。

## 4. 接口契约

### 4.1 样本增删改

`POST /evaluation/datasets/{dataset_id}/cases`、`PUT /evaluation/datasets/{dataset_id}/cases/{case_id}`、`POST /evaluation/datasets/{dataset_id}/cases/batch` 的请求体在原有字段之外增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `turns` | string[] | 用户逐轮话术；空数组表示单轮 |
| `userProfile` | string | 模拟用户画像；空串表示不用模拟器 |

读取样本时字段名为 `turns`（数组）与 `user_profile`（字符串）。

### 4.2 运行汇总

`run.summary` 增加 `avgTurns`（float）。其余字段沿用 S-002。

### 4.3 样本结果

`results[]` 的 `trace` 对象增加 `turns`（int）与 `transcript`（string[]）。

### 4.4 轨迹断言新增键

`type=trace` 的 `expect` 增加 `minTurns` / `maxTurns`：对话总轮数的上下限。其他键沿用 S-002。

### 4.5 门禁 CLI

```
python -m python_backend.eval_gate --target <运行编号> [--base <基线运行编号>] [--db <测评库路径>] [--json]
```

- 退出码：门禁全过 `0`，有未通过项 `1`，运行/基线不存在 `2`。
- 不带 `--json` 时按行打印每条门禁的判定；带 `--json` 时输出完整报告 JSON。
- 门禁配置读自 `evaluation_config.gates`，判定逻辑与 `POST /evaluation/gates/check` 完全一致（同一份 `check_gates`）。

## 5. 行为约定

### 5.1 多轮执行语义

- 样本的首轮输入永远是 `input_text`；`turns` 是**后续**用户话术。
- 脚本模式（有 `turns`）：按顺序把每句话发进**同一个会话编号**，助手逐轮回答。轮数 = 1 + len(turns)。
- 模拟模式（有 `user_profile` 且无 `turns`）：每轮助手回答后，把完整对话交给模拟器生成下一句用户话术。
  - 模拟器返回 `__END__` 或空串 → 对话结束。
  - 模拟器最多让对话走 `max_turns`（默认 8）轮；脚本模式不受此限制，按脚本条数走完。
  - 模拟器默认走项目已有模型能力（`config.settings` + `llm.build_chat_model`），可注入替换（测试用）。
  - 模拟器调用失败一律当作「对话结束」，不中断测评。
- 多轮的所有轮次共用一个会话编号，因此助手能看到前几轮；每轮的事件流单独收集，结束后合并成一份轨迹（计数相加、工具取并集、耗时与 token 累加）。
- 评分对象是**最后一轮**的助手输出；完整对话在 `trace.transcript` 里可查。
- **澄清轮没有正文文本**：助手被需求门闸拦下时产出的是 `clarify` 事件（问题 + 理解方向），正文为空。这类轮次在 `trace.transcript` 里还原成「【需要澄清】问题；方向1；方向2」，避免逐轮输出出现空白。

### 5.2 失败分类与多轮

判定顺序沿用 S-002：`timeout` → `judge_unavailable` → `tool_error` → rubric 声明的 `failureKind` → `unknown`。多轮中任一轮失败即该样本失败，失败原因取该轮。

### 5.3 会话隔离

- 测评会话编号固定以 `eval:` 开头；`Storage.session_list`（用户侧栏数据源）过滤掉 `eval:%`，计数与列表口径一致。
- 测评会话仍写入 `ai_session`，保留可追溯性，只是不进用户侧栏。
- 上下文与记忆按会话编号隔离在 `eval:` 命名空间内，不影响真实会话。

### 5.4 门禁口径唯一

同一份 `gates` 配置、同一份 `check_gates` 实现，被三处复用：Harness 页面、HTTP 接口、CI 命令行。不再出现「发布门禁 vs 评测自检门禁」在同一页并列的情况。

门禁可用指标（`analysis.GATE_METRICS`）必须覆盖 summary 里所有可判定的数值字段：`passRate`、`passAtK`、`flakyRate`、`avgLatencyMs`、`avgTokens`、`avgTurns`、`failedCount`、`caseCount`、`passedCount`、`resultCount`。指标不在表内 → 该条判「指标或比较算子不支持」即未通过；页面「评测配置」的下拉选项与此表一致。

1. **`avgTurns` 门禁恒判未通过**。`analysis.GATE_METRICS` 白名单漏了 `avgTurns`（`avgTokens` 同理），任何以轮数或 token 为阈值的门禁都会落到「指标不支持」分支判未通过。已把两者加入白名单，并在「评测配置」的下拉里补上对应选项；补单测 `test_turn_count_metric_is_supported`。

## 8. 已知限制与后续

- **不是真沙箱**：测评仍跑在真实 Worker 上，占用真实模型额度与执行槽位；并发跑批会和真实用户抢 Worker 容量。
- **多轮成本翻倍**：每一轮都是一次真实模型调用，`epochs` × 多轮会让测评成本成倍上升，样本量要控制。
- **模拟器不稳定**：模型扮演的用户每次说法不同，同一个样本在不同 epoch 下的轮数可能不同——这正是 `flakyRate` 要暴露的东西，但也意味着模拟器样本不适合当严格回归基线。
- **评分只看最后一轮**：如果要看中间某一轮说了什么，得去 `trace.transcript` 里查，没有按轮断言的规则类型。
- **轨迹事件表只展示最后一次执行**：事件表来自样本的 `exec_run_id`（最后一轮），而轨迹摘要里的计数（澄清次数、轮数、token）覆盖全部轮次。
- **CI 门禁未接流水线**：CLI 已可用，但仓库没有 CI 配置，需要人工或外部流水线调用。
