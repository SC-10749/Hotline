# 变更规格索引（spec）

> 本目录是 Hotline 的**变更规格库**：每次改动代码、接口或方案，都在这里留下一份规格，作为后续功能与接口改动的约束来源。
> 规则原文见根目录 `AGENTS.md` 的「规格驱动变更」一节。

## 开工前必读

1. 先读本索引，看有没有正在生效、且与本次改动相关的规格。
2. 再读相关规格正文（文件名列在下方表格里），确认接口字段、行为约定与验收标准。
3. 若本次改动会让已有规格失效或需要扩展，先改规格，再改代码；两者冲突时**以代码为准**，并当场把规格修正回来。

## 两层文档：模块现状 vs 变更契约

| 层 | 位置 | 回答什么问题 | 生命周期 |
| --- | --- | --- | --- |
| 模块功能规格 | [modules/index.md](modules/index.md) | 这个模块现在有什么功能、入口在哪、有什么约束 | 长期有效，随实现更新 |
| 变更规格 | 本目录根 | 这次改动定下了什么契约、验收标准是什么 | 一次改动一份，被取代则标「已废弃」 |

改动落到哪个能力模块，先读那份模块文档；涉及接口、表结构、跨模块语义，再另立变更规格。

## 写规格的最小要求

- 一次改动一份文件，命名 `YYYY-MM-DD-<短标题>.md`；编号按 `S-001` 递增，写进本索引。
- 必须写清：背景与目标、非目标、数据模型变更、接口契约（字段级）、行为约定、验收标准、验证记录、已知限制。
- 不写实现过程流水账，不贴大段代码；只写「改完之后世界应该是什么样」，让下一个接手的人或 AI 能据此判断改动是否跑偏。
- 状态只用三种：**草案**（还没动手）、**已实现**（代码已落地且验证通过）、**已废弃**（被新规格取代，保留供追溯）。

## 与其它文档的关系

- 规格说「这次改动定下了什么契约」，设计文档说「为什么这么设计」，README 说「现在整体是什么样」。
- 规格被设计文档细化是正常的；规格与 README 冲突时，以代码和规格为准，README 随后修。
