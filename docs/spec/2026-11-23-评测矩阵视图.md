# 规格 S-006：评测矩阵视图

> 状态：已实现
> 日期：2026-11-23
> 背景依据：[评测能力差距清单](../../evaluation-gap-analysis.md)（能力项 7 相对判定、8 多变体矩阵对比、22 可评覆盖率）、[顶级高星项目的评测是怎么做的](../../evaluation-practices.md)
> 影响范围：`python_backend/modules/evaluation/matrix.py`（新增）、`python_backend/api/routers/evaluation.py`、`frontend/src/api.js`、`frontend/src/modules/evaluation/matrix.js`（新增）、`frontend/src/modules/evaluation/AgentEvalPanel.vue`、`docs/spec/modules/evaluation.md`、`docs/evaluation.md`

## 1. 背景与目标

现有评测对比只有两个入口，且都只看「两次运行」：

- `GET /evaluation/runs/compare?base=&target=` —— 两次运行的汇总 diff + 逐样本 improved/regressed。
- Agent 测评页的「结果明细」 —— 单次运行的样本列表。

缺的是**多轮运行 × 样本的并排矩阵**：改了 prompt、换了模型、调了 rubric 之后，**同一条样本**在几次运行里分别判成什么，一眼要能横向看。这正是 promptfoo 之类工具的招牌能力，也是本项目 S-005 语义分落地后的直接需求（「改 prompt 会不会退化」）。

本规格做三件事：

- 后端提供矩阵聚合接口：多 run × 样本，每格是判定与分数，每行给出相对基线的变化与同题择优结果。
- 每列给出可评覆盖率（有多少样本真的被判过分），和通过率并列，避免「通过率高但一半没判分」的假象。
- 前端在 Agent 测评面板里出矩阵视图：勾选若干运行 → 一张表看全。

## 2. 非目标

- **不做模型判定的两两对战**（同一题两版答案让模型直接判谁更好）。矩阵里的相对判定基于各轮已得的分数，不额外消耗模型额度；模型对战需要额外的长度去偏设计，另立规格。
- **不做置信区间与噪声阈值判定**。矩阵只给「哪列更好、这一题是否稳定」，不给统计显著性。
- **不做定期回归任务与基线 diff 快照**（nightly 重跑、结果快照进版本库）。
- **不做样本合成与红队**（S-007）。
- 不引入外部评测框架，不新增 pip/npm 依赖。

## 3. 数据模型变更

无表结构变更。矩阵是**读取期聚合**：输入是已有的 `evaluation_run` 记录与 `evaluation_result` 行，不落库。

## 4. 接口契约

### 4.1 新接口 `GET /evaluation/runs/matrix`

请求：`runs` 查询参数，逗号分隔的运行编号，**2 至 8 个**，顺序即矩阵列顺序，**第一个是基线**。

响应：

```json
{
  "sameDataset": true,
  "runs": [
    {"runId": "eval-a", "agent": "chat", "status": "completed",
     "datasetId": "dataset-a", "epochs": 1, "createdAt": "...",
     "passRate": 0.8, "graded": 4, "total": 5, "coverage": 0.8}
  ],
  "rows": [
    {
      "caseId": "case-1",
      "cells": [
        {"runId": "eval-a", "verdict": "passed", "score": 1.0, "graded": true,
         "epochs": 1, "passedEpochs": 1, "failureKind": "", "change": "unchanged",
         "metrics": {"answer_relevance": {"score": 0.9, "detail": "…", "judge": "…"}}
      ],
      "best": {"runId": "eval-b", "score": 1.0, "verdict": "passed"}
    }
  ],
  "summary": {"eval-a": {"graded": 4, "total": 5, "coverage": 0.8, "passed": 3, "failed": 1}}
}
```

| 字段 | 说明 |
| --- | --- |
| `runs[].runId` | 运行编号 |
| `runs[].coverage` | 可评覆盖率 = 已判分样本数 / 该 run 的样本数 |
| `rows[].cells[]` | 该样本在该 run 下的一格 |
| `cells[].verdict` | `passed` / `failed` / `flaky`（多轮有对有错）/ 其它原判定值 |
| `cells[].change` | 相对基线列的变化：`unchanged` / `improved` / `regressed` / `added`（基线没有此题）/ `removed`（此 run 没有此题） |
| `cells[].graded` | 是否真的判过分（见 4.2） |
| `rows[].best` | 同题择优：该样本得分最高的运行（同分取先出现者） |

### 4.2 多轮结果的合并口径

一个样本在一次运行里可能有多轮（`epochs`）。矩阵一格合并这些轮次：

- 全部轮次通过 → `verdict=passed`；有对有错 → `flaky`；无通过且含失败 → `failed`；其余按 `timeout` → `invalid_rubric` → `scorer_unavailable` → `not_scored` → `skipped` 取首个命中的值。
- `score` 取各轮均分；`epochs` 是轮数；`passedEpochs` 是通过轮数。
- `failureKind` 取首个非空值；`metrics` 按指标名合并，各格取首次出现的值。

### 4.3 可评覆盖率口径

`graded` 的判定集合是 `{passed, failed, flaky}`——只有真的判过分才计入覆盖率。
`timeout` / `invalid_rubric` / `scorer_unavailable` / `not_scored` / `skipped` 都不计入（没判分不是失败，也不是通过）。

## 5. 行为约定

- 少于 2 个运行编号返回 400；多于 8 个返回 400；任一运行编号不存在返回 404，提示具体编号。
- 矩阵行是各运行样本编号的并集，按编号排序；某个运行没有这条样本时该格标为 `removed`。
- 不同测评集的运行可以放进同一张矩阵，`sameDataset=false` 时由页面提示「不同测评集」，不阻止查看。
- 基线取 `runs` 里的第一个；相对判定只看「是否通过」，不看分数高低（同为未通过即 `unchanged`）。
- 同题择优按分数取最高；同分取列顺序靠前的运行。
- 矩阵是只读视图，不改写任何运行与结果数据，也不触发重跑。
- 覆盖率与通过率并列展示，口径与 `summary` 字段一致；两者分母不同（覆盖率的样本数、通过率的已判分数），页面要分别标注。

## 6. 验收标准

- [ ] `GET /evaluation/runs/matrix?runs=a,b` 返回矩阵，行是样本并集、列是运行，格子含判定与分数。
- [ ] `cells[].change` 正确给出 improved / regressed / unchanged / added / removed。
- [ ] 同题择优 `rows[].best` 指向得分最高的运行。
- [ ] 可评覆盖率与通过率分别给出，口径符合 4.3。
- [ ] 运行数少于 2 或多于 8 返回 400；运行不存在返回 404。
- [ ] 前端矩阵视图能勾选多次运行并渲染表格，单元格显示判定与分数。
- [ ] 矩阵视图不改动任何评测数据。

## 8. 已知限制与后续

- 相对判定只看通过与否，不做分数高低比较，也不做模型对战。
- 行标签是样本编号，不显示样本正文；需要正文时另开样本详情。
- 「定期回归任务」「基线 diff 快照」「置信区间」留在后续规格：前两者需要一个定时任务与结果快照的存储约定，置信区间需要先定样本量口径。
