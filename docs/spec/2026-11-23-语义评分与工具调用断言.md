> 状态：已实现

> 背景依据：[评测能力差距清单](../../evaluation-gap-analysis.md)
> 影响范围：`python_backend/modules/evaluation/semantics.py`（新增）、`python_backend/modules/evaluation/analysis.py`、`python_backend/modules/evaluation/__init__.py`、`python_backend/api/routers/evaluation.py`、`python_backend/llm.py`、`python_backend/infrastructure/evaluation_store.py`（`evaluation_result` 增 `metrics` 列）、`frontend/src/api.js`、`frontend/src/modules/evaluation/AgentEvalPanel.vue`、`frontend/src/HarnessApp.vue`、`docs/spec/modules/evaluation.md`

## 1. 背景与目标

S-002 / S-003 / S-004 已经把评测的**过程**、**多轮**、**规模**三块补齐：轨迹断言能验澄清与工具、多轮能验对话、并行与预算能验规模。
但缺口清单指出当前只能验「有没有做」，验不了「做得对不对」：

1. **没有语义指标**。`rubric.type=model` 是一条通用判分通道，要写 criteria 才能用；没有现成的「话题跑偏」「答非所问」「事实一致性」这类可复用指标，对齐不了 deepeval / ragas 的指标库。
2. **工具调用只验名字**。`expectTools` 能说「调过 retrieval」，但说不了「调对没有、参数对不对」——这是 ragas `tool accuracy` 的核心。
3. **判分结果无处可看**。语义分只有一个 0/1 的 `verdict`，看不出「哪个维度掉了」。

本规格做三件事：

- 新增 `semantic` 评分类型与首批内置语义指标模板（走现有模型判分通道，不新增依赖）。
- 轨迹断言补参数级工具调用断言（规则型，不耗模型）。
- 语义判分结果带维度明细，能在样本编辑与结果明细里看到。

同时把「下一阶段优先级」固化进规格（见第 2 节），避免每轮重新讨论。

## 2. 下一阶段路线图

完整差距矩阵见 [评测能力差距清单](../../evaluation-gap-analysis.md)。本项目后续规格的顺序与理由：

| 顺序 | 规格 | 主题 | 交付形态 |
| --- | --- | --- | --- |
| **本规格（S-005）** | 语义评分与工具调用断言 | 新 rubric 类型 `semantic` + 内置指标模板 + 参数级工具断言 + 维度明细 + 评委可配 |
| S-006 | 变异矩阵对比 + 相对判定 + 可靠性口径 + 可评覆盖率 + 定期回归 | 多 run × 样本矩阵视图、同题择优、`pass@k`、置信区间、可评覆盖率、基线 diff 与回归任务 |
| S-007 | 样本自动合成 + 人工标注回流 + 安全红队 + 多维风险指标 | 从知识库合成用例；标注回流闭环；红队话术模板（注入 / 越权 / PII / 越狱）；安全 / 毒性 / 稳健性维度 |
| S-008 | 评测沙箱隔离 + CI 流水线 + 成本报表 | 隔离工作目录、GitHub Actions、成本汇总 |
| S-009 | 任务集 / 环境注册表 | 长程工具任务集模板（Toolathlon / BFCL 风格）+ 为具身预留接口，只留抽象不实现 |
| S-010（候选） | 在线评估与回归监控 + OTel 出口 | 生产 trace 上的评测规则、OpenTelemetry 导出 |

排序依据：S-005 是「评测有效性」的地基；S-006 需要语义分才有对比价值；S-007 需要 S-005 的合成样本才谈得上覆盖度；S-008 在样本量与并发上来之前不急；S-009 形态差一个量级，只留口。

## 3. 非目标

- **不引入外部评测框架**（Inspect AI / promptfoo / deepeval / ragas 都不引入），语义指标自己实现，可对标不照搬。
- **不做 YAML DSL**，rubric 继续用 JSON。
- **不做 S-006 的矩阵视图**，本规格只把判分结果准备好。
- **不做合成与红队**（S-007）。
- **不做沙箱与 CI**（S-008）。

## 4. 数据模型变更

无表结构变更。

- `evaluation_result.trace` 增加 `toolCalls` 数组：每次工具调用的 `{tool, args}` 摘要。
- `evaluation_result` 增加 `metrics` 字段（JSON）：语义判分的维度明细，例如 `{"topic_adherence": {"score": 0.8, "detail": "…"}}`。

## 5. 接口契约

### 5.1 新 rubric 类型 `semantic`

```json
{"type": "semantic", "metric": "topic_adherence", "expect": {"topics": ["客服系统"]}}
```

| 字段 | 说明 |
| --- | --- |
| `metric` | 语义指标名，取自内置模板库；未知指标判 `invalid_rubric` |
| `expect` | 指标参数，随指标而定（见 5.2） |
| `judgeModelId` | 判分模型（模型路由里注册的模型 id）；留空用默认判分模型 |

内置指标共四个（模板由 `modules/evaluation/semantics.py:SEMANTIC_METRICS` 定义，页面通过 `GET /evaluation/semantic-metrics` 取列表）：

| metric | 衡量 | expect 参数 | 判分方式 |
| --- | --- | --- | --- |
| `topic_adherence` | 回答是否停留在约定话题域内 | `topics`（字符串数组，必填） | 模型判分 |
| `answer_relevance` | 是否答非所问 | 无 | 模型判分 |
| `fact_consistency` | 回答与给定依据是否一致 | `context`（字符串数组，必填） | 模型判分 |
| `trajectory_quality` | 过程是否走对：有没有漏掉必要步骤、有无绕路 | `mustTools`（字符串数组，可选）、`maxSteps`（int，可选） | 模型判分，输入含轨迹摘要 |

判分通道复用 `score_with_model`：模板把 `metric` 渲染成 criteria 文本，连同 `expect` 与实际输出交给模型，要求返回 `{"score":0-1,"verdict":"passed|failed","reason":"…"}`。模型不可用时记 `scorer_unavailable`，不伪造分数。

### 5.2 轨迹断言新增键

`type=trace` 的 `expect` 增加：

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `expectToolCalls` | 对象数组 | 期望的工具调用：`{"tool": "检索", "argsContain": ["关键词"], "argsMatch": {"limit": 5}}` |
| `minToolCalls` | int | 工具调用次数下限 |

匹配规则：`tool` 精确匹配；`argsContain` 里每个字符串都要出现在该次调用的参数里；`argsMatch` 的键值要等于该次调用参数里的同名键。全部期望都满足才算通过。

### 5.3 评委可配

- 语义判分用的模型必须可换：`judgeModelId` 指向模型路由里注册的模型 id。
- `llm.py` 增加按模型 id 构建对话模型的入口（复用已有的模型注册表与客户端参数，不新增配置体系）。
- 找不到该 id 时判 `invalid_rubric`（配置错误），**不静默换回默认评委**——静默替换会让不同样本用不同评委，分数无法比较。
- 判分结果里记录实际用的评委（`metrics[metric].judge`），事后能按评委分组做一致性校准。

### 5.4 轨迹摘要里的工具调用

`build_trace` 额外收集 `toolCalls`（每次工具调用一条 `{tool, args}`）：

- `tool` 取工具名；
- `args` 取调用参数，**只保留键名与值的前 40 个字符**（脱敏，不落凭据、不落整段原文）；
- 凭据类参数（键名含 token / secret / password / credential / apikey 等）整条丢弃，不留占位值；
- 没有参数的调用 `args` 为空对象。

### 5.5 语义判分明细

`POST /evaluation/runs/{id}` 与 `GET /evaluation/runs/{id}/trace` 返回的结果项增加 `metrics` 字段：`{指标名: {"score": 0-1, "detail": "理由", "judge": "评委名", "label": "指标中文名"}}`。`multi` 规则里每个语义子规则的明细合并进同一个 `metrics`。`metrics` 随结果落库（`evaluation_result.metrics` 列），`GET /evaluation/runs/{id}` 的结果项直接带出。

新增接口：`GET /evaluation/semantic-metrics` —— 返回内置指标模板列表（`metric` / `label` / `required` / `instruction`），供样本编辑时选模板。

## 6. 行为约定

- 语义评分**消耗模型额度**，与现有 `type=model` 一致；规则型断言（`type=trace`）不消耗。
- 语义指标不可用（模型超时、返回非法 JSON）时该样本记 `verdict=scorer_unavailable`、`failure_kind=judge_unavailable`，不静默判通过。
- 语义指标缺少必填 `expect` 参数、或指标名不在模板库里，记 `invalid_rubric`，不算失败样本。
- `judgeModelId` 指向的模型在模型路由里不存在时记 `invalid_rubric`，**不静默换回默认评委**。
- 一个样本可以同时用语义 rubric 与轨迹 rubric（用 `multi` 组合，`mode=all`）。
- 工具调用参数只留前 40 字符，不落原文；参数里若出现疑似凭据（键名含 token / key / secret / password）直接丢弃该值。
- 轨迹断言是规则判定，不因语义评分失败而改变，两者在 `multi` 里各自独立。
- `trajectory_quality` 的判分输入是「轨迹摘要（工具序列、步骤数、澄清次数）+ 最终输出」，由评委一次判定；轨迹不可用时该样本判 `not_scored`，不猜。
- 做法依据见 [顶级高星项目的评测是怎么做的](../../evaluation-practices.md)：语义轨迹评分对应 LangChain / LangGraph 的 trajectory evaluator，可评覆盖率与相对判定排在 S-006。

## 7. 验收标准

- [ ] `semantic` rubric 在模型可用时给出 score/verdict/detail，并写进结果的 `metrics`。
- [ ] 未知 `metric` 判 `invalid_rubric`；模型不可用判 `scorer_unavailable` 且不伪造分数。
- [ ] `expectToolCalls` 能断言工具名与参数（含 `argsContain` / `argsMatch`），不满足时 detail 指明差在哪一项。
- [ ] `minToolCalls` 生效。
- [ ] 轨迹摘要里出现 `toolCalls`，参数只留前 40 字符，凭据类参数值被丢弃。
- [ ] `multi` 里混用语义与轨迹子规则时，两侧结论各自正确。
- [ ] `judgeModelId` 能指定判分模型；找不到该 id 时判 `invalid_rubric` 而不是静默换默认评委。
- [ ] `trajectory_quality` 能区分「终答对但漏了必要步骤」；轨迹不可用时判 `not_scored`。
- [ ] 判分结果记录实际评委（`metrics[metric].judge`），可按评委分组比较。
- [ ] 页面能选内置语义指标模板并填 `expect`，结果明细能看到维度明细。

## 9. 已知限制与后续

- 语义分数有噪声：同一份答案两次打分可能差 0.1 以内，比较时看均值差。
- 首批指标只覆盖「话题 / 相关性 / 事实一致性」三类；deeper 的 faithfulness、hallucination、bias、toxicity 等留在后续。
- 语义评分跑在真实 Worker 上，会和用户抢模型额度；建议配合 S-004 的预算护栏。
- 后续 S-006 的矩阵对比会直接消费本规格产出的 `metrics` 字段。
- 本机模型路由表默认为空，`judgeModelId` 需要先在「模型路由」页登记模型才能使用。
