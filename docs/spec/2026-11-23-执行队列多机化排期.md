# 规格 S-010：执行队列多机化（排期草案）

> 状态：草案
> 日期：2026-11-23
> 影响范围：`python_backend/infrastructure/queue.py`、`python_backend/modules/execution/`、`docs/spec/modules/execution.md`

## 1. 背景与目标

执行队列当前是**单机 SQLite**（`data/execution.db`），多 Worker 进程靠 SQLite 事务抢占来分配运行。这套机制在本机成立，但有两个硬边界：

1. **不能跨机**。SQLite 文件不能被多台机器同时安全写入，Nacos 注册发现虽然能发现多实例，但它们各自的队列互不相通——请求落到 A 机，A 机队列里的运行 B 机看不见。
2. **并发上限受限于本机磁盘 IO**。`HOTLINE_PYTHON_WORKER_INSTANCES` 决定并发运行数上限，再往上加 Worker 只是让 SQLite 抢占更频繁。

本规格不实现多机执行，只把**下一步怎么做**写清楚，避免后续重新讨论。

## 2. 非目标

- **本规格不写代码**：只定方向、接口边界与验收口径。
- **不引入新中间件**：MySQL / Redis 已是可选依赖，不为队列再引入 Kafka / RabbitMQ。
- **不改现有单机行为**：SQLite 路径继续可用，不强制迁移。

## 3. 当前实现现状

| 事实 | 位置 |
| --- | --- |
| 队列是单机 SQLite，靠事务抢占分配运行 | `python_backend/infrastructure/queue.py` |
| 运行表带 `parent_run_id` / `slot` / `workspace_root`，活跃唯一索引是 `(conversation_id, slot)` | 同上 |
| 多 Worker 靠 `HOTLINE_PYTHON_WORKER_INSTANCES` 起进程，各自在同一文件上抢占 | `java_backend` 的 `PythonProcessLauncher` |
| Redis 已能承载分布式任务锁与停止广播 | `python_backend/modules/execution/engine.py` 的 `TaskManager` |

也就是说：**锁与广播已经能跨机，队列还不能**。缺的是最后这一块。

## 4. 候选方向与取舍

| 方向 | 改动量 | 能跨机 | 代价 |
| --- | --- | --- | --- |
| A. 队列换 MySQL | 中 | 是 | 需要重写抢占逻辑（`SELECT ... FOR UPDATE SKIP LOCKED`），但项目已有 MySQL 适配层 |
| B. 队列换 Redis | 中 | 是 | 需要自己实现可靠队列与持久化 |
| C. 引入 Kafka 等 | 大 | 是 | 为当前规模过度设计 |

**倾向 A**：MySQL 适配层已经存在（`modules/storage/relational.py`），存储后端本身也支持 `DODO_STORAGE_BACKEND=mysql`，复用现有方言抽象能少写一半代码。

## 5. 实施顺序（后续排期）

1. 抽出队列接口：把 `SqliteExecutionQueue` 的读写拆成 `ExecutionQueue` 协议，两种实现都实现它。
2. 实现 `MySqlExecutionQueue`：用 `FOR UPDATE SKIP LOCKED` 做抢占，沿用现有 MySQL 方言封装。
3. 事件持久化与运行状态迁到 MySQL，注意 `evaluation` 与 `retention` 模块对 `execution.db` 的直接依赖要一起改。
4. 多机验收：两台机器各起 Worker，验证运行可被任意 Worker 领取、停止广播跨机生效、并发子任务的 `slot` 互斥在跨机下仍成立。

## 6. 验收标准

（本规格实施后回填）

1. 同一会话的活跃运行唯一性在跨机下仍由 `(conversation_id, slot)` 保证。
2. 停止信号能跨机到达任意 Worker。
3. 单机 SQLite 路径仍可用，且与 MySQL 路径行为一致。
