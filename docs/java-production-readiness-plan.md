## 0. 实现语言与所有权：Java 主导业务治理

**本方案要求新增的认证、权限策略、限流、业务配额、提交台账、审批、调度、发布决策和管理 API 由 Java 实现。** Java 不只是把这些请求转发给 Python。AI 推理、解析、检索、Agent 编排与工具执行继续复用 Python。

| 分类 | Java 实现范围 | Python 是否需要配合 |
| --- | --- | --- |
| Java 独立治理 | Java 请求过滤、实例并发池、入口速率限制、熔断、配置校验、治理指标 | 可先保护经过 Java 的流量；Python 直连必须由部署策略限制 |
| Java 业务权威 | 用户/租户/ACL、额度账本、提交台账、调度规则、审批单、发布策略、模型路由政策 | 校验内部身份、接收稳定 ID 与策略版本、返回执行事实；不能维护第二份可写政策 |
| 跨端一致性 | Java 编排幂等提交、额度结算、查询投影和业务通知 | Python 提供提交去重、实际用量、单调事件版本与状态查询，才能形成闭环 |
| Python 执行基础设施 | Java 提供准入、业务查询、恢复操作的授权入口 | 共享执行队列、租约 fencing、解析/检索隔离和工具沙箱必须在 Python/Worker 实现；J13 并非 Java 独立功能 |

因此，“采用 Java 治理技术”不等于“Python 零改动”。若要求完全不改 Python，只能交付入口保护，不能承诺端到端租户隔离、准确 Token 硬预算、多机执行恢复或外部副作用幂等。后续每项均标出配合边界。

## 1. 当前基线与主要差距

| 已核对位置 | 当前行为 | 建设含义 |
| --- | --- | --- |
| `java_backend/pom.xml` | Java 21、Spring Boot 3.5.16、Web、Validation、Nacos Discovery；未声明 Spring Security、Redis、治理组件或业务数据库依赖 | 先补治理闭环，无需先拆微服务 |
| `java_backend/src/main/resources/application.yml` | 虚拟线程、优雅停机；连接与请求超时配置 | 虚拟线程降低等待成本，但不增加数据库、模型和 Worker 的容量 |
| `trigger/http/PythonCapabilityController.java` | 转发 Agent、执行、文件、会话、技能、评测等路径 | 这些路径需要分别定义授权和资源预算，不能全部采用同一套 QPS |
| `infrastructure/gateway/PythonHttpGateway.java` | 共享 JDK HttpClient、流式请求体与响应体、SSE flush、保留上游状态；允许转发 Authorization 和 Last-Event-ID | 目前是协议转发；转发认证头不等于验证身份；流式请求体不天然可重放 |
| `infrastructure/gateway/PythonEndpointResolver.java` | 静态寻址或 Nacos；过滤 apiVersion、draining，再轮询选实例 | 已有发现能力，尚不能据此宣称端到端故障切换或容量感知调度 |
| `trigger/http/CapabilityController.java` → `application/CapabilityService.java` → `infrastructure/adapter/port/PythonCapabilityAdapter.java` | live 检查 Java 自身，ready 调用 Python 就绪接口 | 应保持存活与就绪分离，避免下游故障触发 Java 重启风暴 |
| `python_backend/modules/execution/store.py` | SQLite 任务与事件、领取、Worker 心跳、租约；领取时处理过期任务 | 是同机执行基础，不是多机共享队列或外部副作用恰好执行一次 |
| `python_backend/application/execution_service.py`、`python_backend/infrastructure/queue/sqlite.py`、`python_backend/workers/execution_worker.py` | 用例、队列适配、独立 Worker | 多机化要覆盖 API 与 Worker 两侧，Java 扩容不能替代这项改造 |

上表 Java 路径省略的共同前缀为 `java_backend/src/main/java/cn/hotline/`。现状范围限于这些代码及依赖声明，不据此推断所有 Python 路由都没有任何保护。

代表请求链：浏览器 → `PythonCapabilityController.forward` → `PythonHttpGateway.forward` → `PythonEndpointResolver.resolve` → FastAPI → 执行用例/队列 → Worker；事件再经 SSE 返回。Java 新增身份、授权与准入应位于向 Python 发起请求之前，执行数据隔离与副作用保护仍须在 Python/Worker 落实。

## 5. 关键设计如何落地

### 5.1 身份与权限：角色决定动作，归属决定数据

建议采用租户 → 工作区 → 会话/文档/任务/产物的资源层级；最小角色为 owner、admin、member、viewer。角色名和权限点是建议，实施前与产品范围对齐。权限点可从 `execution:create/read/cancel`、`document:upload/read/delete`、`skill:manage`、`evaluation:run` 开始。

Java 校验用户身份、成员关系与动作权限，Python 在查询和执行入口复核可信身份与资源范围。检索、记忆、向量结果、执行事件及产物元数据均带 tenantId/workspaceId；查询必须带作用域条件，不能先全量读取后在前端过滤。单用户历史数据需要明确归属迁移。

浏览器传来的 X-Tenant-Id 等上下文不能直接信任。Java 删除或覆盖外部身份头，再生成 audience、有效期、主体与租户范围受约束的内部凭证；Python 验证凭证，内部网络访问也须受控。任务入队保存授权所需上下文；运行高危工具前按策略复核撤权，避免任务排队期间权限变化失效。

若使用 Cookie 会话，保持 CSRF 防护并规划跨副本会话存储；原生 EventSource 无法像普通 fetch 任意设置 Authorization 头，需采用同源安全会话或支持认证头的流读取方式。不要把长期令牌放到 URL。JWT 方案需明确撤销、密钥轮换与权限缓存失效，不能只做签名验证。

### 5.2 限流、并发、配额与背压分开设计

- **速率**：每租户/用户/接口每秒接受多少次，Redis Lua 实现令牌桶或固定窗口；固定窗口需承认边界突刺。
- **在途并发**：实例总连接、租户 SSE、上传及提交请求分别控制。Semaphore 保护实例；跨实例租户并发若用 Redis 租约，需唯一持有者、续约和条件释放，并处理租约过期而连接仍存活的超额窗口。不能声称绝对不超限。
- **成本配额**：模型 Token、文件字节、任务数按资源扣减；硬配额在持久化台账中原子预占，结算带唯一业务号。Redis 只作加速或软预算时不能承担唯一账本。
- **背压**：限制排队数量、等待时间和单请求大小；有空闲才接收，超限拒绝。等待者数量也要限制，不能仅用 tryAcquire(timeout) 留下无限等待者。

建议执行顺序：请求大小与匿名粗筛 → 认证 → 资源授权 → 租户速率 → 幂等查询/占位 → 成本预占 → 并发准入 → 下游调用。后续失败需要按状态机释放占位/预占；同一幂等请求的重放不能重复收费。上传应在大体积读取和模型调用前尽早校验。

多实例共享计数要约束键的基数与 TTL；同一原子脚本涉及多键时，Redis Cluster 键需要同槽。Redis 不可用时：高危执行与硬成本新提交应拒绝；低风险只读可进入更保守的本地限流。故障策略必须配置化并演练，不允许无条件放行。

租户超限建议返回 429；依赖不可用或系统容量不足可返回 503；未认证 401、无权限 403。资源存在性敏感时可统一 404。外部错误只暴露安全诊断，不带内部地址、异常栈或令牌。

### 5.3 高并发：优化真正受限的资源

保留 Spring MVC + Java 21 虚拟线程，先测量后决定是否需要响应式重写。当前 JDK HttpClient 复用与流式转发可继续使用；连接、文件描述符、堆内存、CPU、数据库连接、模型配额仍需要独立预算。

容量初估可用稳定系统下的 Little 定律：平均在途量约为吞吐 × 平均停留时间；这只是平均关系，不应用 p99 相乘当作严格容量公式。SSE 活跃连接数与 Worker 运行任务数分开计量；一个任务可有多个订阅者，一个连接也不应占用执行槽位。

给 SSE、上传、交互提交和批量评测设不同隔离池；限制慢消费者的缓冲与写等待，不能为每个连接缓存整段事件。Python 侧同时治理同步 I/O、摄取批处理与事件轮询读放大。增加 Java 线程或实例无法解决这些下游瓶颈。

### 5.4 超时、重试与熔断

当前 `PythonHttpGateway` 使用请求 timeout 并通过 InputStream 读取响应，不应假定这个设置完整覆盖整个流的空闲读取和总时长；需用慢响应头、卡住响应体、持续心跳等测试分别核验。

普通接口设置调用总预算与连接预算；SSE 分别设置响应头等待、空闲检测和最大连接寿命，心跳应短于反向代理空闲超时。请求取消要停止上游读取、释放连接与并发许可；浏览器断线默认不等于取消已持久化后台任务，取消任务用显式受权接口。

只对明确无副作用且可重放的调用启用少量重试；退避加入随机扰动，所有尝试共享总截止时间。任务提交必须先建立端到端幂等；上传不默认缓存大文件来换取重试。SSE 发出响应头后发生故障，应关闭并让客户端按游标重连，不能改写 HTTP 状态或重新执行。

熔断按依赖/操作分类，不把 401、403、主动 429、客户端取消直接计为依赖故障。SSE 要分别记录建连失败与流中断，不能简单用整个任务时长判定“慢调用”。熔断状态本地化时多副本可能不同步，应在运维指标中体现。

### 5.5 幂等、队列与一致性

Java 建议新增提交台账：`tenant_id + operation + idempotency_key` 唯一约束，记录请求摘要、状态、runId 和有效期。同键同摘要返回原结果，同键不同摘要返回 409；处理中返回可查询状态。超时后先查询对账，不直接创建第二个任务。

Java 台账与 Python 入队是跨服务双写：Python 创建任务也必须接受稳定 submissionId 并做唯一约束，保证响应丢失后可以查回。若演进为异步提交，可采用事务 Outbox + 消费端 Inbox/唯一键，并带重投、对账与失败恢复。只在 Java 加锁或记录 Redis 键不能解决双写断点。

多机队列沿用架构草案优先评估 PostgreSQL，采用事务领取/行锁跳过已锁记录、租约与递增 fencing token；续租、写事件、完成都校验持有者和 token。任务消息按至少一次交付设计，外部写操作仍要幂等或补偿。租约防旧 Worker 写回，不保证外部服务绝不重复执行。

API、Worker 共用执行数据库和对象存储，事件以 runId 与单调序号定位。通知可以用 Redis 唤醒，但持久事件表才是回放依据；通知丢失后可以补查。暂不为了展示技术栈引入 Kafka/RocketMQ；当吞吐、事件消费或保留需求证明有必要时另做选型。

### 5.6 高可用与运维

目标拓扑为负载均衡 → Java 多副本 → Python API 多副本 → Worker 池，并配套共享数据库/对象存储。只有 Java 多副本不能称为系统高可用；Nacos 发现也不提供业务状态复制。

发布时先摘流，再等待普通请求完成；SSE 给排空截止，截止后让客户端通过其他实例回放。Worker 停止领取后完成或按策略中止在途任务。数据库迁移先扩展再收缩，旧新版本兼容；回滚演练包含任务格式与事件格式，而不只是回滚镜像。

live 仅判断进程是否需要重启；ready 判断能否接受对应工作。Worker 离线时当前 ready 会失败，生产设计需进一步区分“可读”和“可提交”，避免执行链故障连带切断任务查询与取消。监控、取消和健康能力必须保留独立容量。

对数据库备份做实际恢复演练，确定 RPO/RTO；Redis、Nacos 和对象存储分别说明故障影响。限流、权限、缓存和任务真相各有恢复策略，不能统一降级放行。

## 7. 可观测性与验收

指标建议：HTTP p50/p95/p99 与错误率、活跃 SSE、准入等待/拒绝、各池容量与使用量、队列深度与最老任务年龄、Worker 利用率与租约过期数、任务成功率、Token 预占/实际消耗、重试和熔断次数、数据库连接等待、缓存命中率。普通 HTTP 延迟、SSE 首事件时间、流存活时间和任务完成时间分别统计。

低基数标签使用路由模板、操作类、结果类；userId、runId、sessionId 不作为常规时序标签，放到受控追踪或审计记录。日志和审计均不得记录原始令牌、真实服务地址、完整提示词或敏感文件内容。

可采用 Micrometer → Prometheus 协议采集 → VictoriaMetrics → Grafana，并评估 vmagent/vmalert；这属于待部署方案，当前不宣称已接通。指标平台与业务鉴权分工明确，vmauth 的代理认证不能替代 Hotline 资源权限。

| 验收场景 | 执行方式 | 判定依据 |
| --- | --- | --- |
| 双副本共享限流 | 同一租户轮流请求两个 Java 实例 | 配额合并计算；超限明确拒绝，不因实例数翻倍 |
| 跨租户访问 | 替换 session/run/file/workspace ID，覆盖读、写、取消、SSE、下载 | 所有入口拒绝越权，且不泄漏资源内容 |
| 慢上游与慢客户端 | 分别阻塞响应头、响应体及客户端消费 | 等待/缓冲有界，取消后许可归还；普通查询保持约定 SLO |
| 提交响应丢失 | Python 入队成功后模拟链路断开，再同键重试 | 一个 submission 对应一个 run，不重复收费 |
| Worker 崩溃与旧 Worker 复活 | 领取后终止进程，等租约处理，再模拟旧 token 写回 | 状态符合恢复策略；旧 token 写回被拒绝；副作用可对账 |
| 多实例 SSE 恢复 | 订阅中终止 Java/Python 实例，带游标连接另一实例 | 事件可回放，客户端能去重，不重建任务 |
| Redis/Nacos/数据库故障 | 分别隔离依赖并恢复 | 按已定义策略拒绝或降级；不放开权限、硬配额或无限重试 |
| 过载与公平性 | 递增并发，同时注入批量评测与交互请求 | 容量受控、无持续内存增长；小租户与控制面仍有服务机会 |
| 发布与恢复 | 执行摘流、排空、版本回滚和备份恢复 | 数据/事件兼容，恢复时间和数据损失有记录 |

先通过现有压测入口与测试工具核定基线，再约定数字目标；不预写“万级 QPS”“零丢失”或“99.99% 已实现”。SLO 应分别定义普通 API、任务准入、任务成功和流恢复；预期 4xx 拒绝另列统计，但不要借排除过载拒绝掩盖用户不可用。

首次容量报告需固定机器 CPU/内存、实例数、数据库、模型桩或真实模型、数据规模、请求比例、测试时长、预热和成功率口径。以稳定负载下的分位延迟与饱和点验收，而不是单次最高吞吐。

## 10. 原有 20 项：功能、设计、实现与结果

以下类名、表名和 API 均为建议。Java 类按现有四层组织；新增对外 API 统一放到待建设的 `/api/v1`，切换前旧代理路径也必须执行相同准入策略。数据库采用架构草案建议的 PostgreSQL，先接入数据源与版本化迁移，再建设业务表；不直接访问 Python 私有表。

### J01～J03：身份、权限与跨端信任

**实现功能**：用户登录后只能操作所在租户及授权工作区；Python 能识别可信主体。

**设计**：Java 是身份与权限权威；初期单一身份接入方式，避免同时维护自建密码系统、OIDC 和多种会话模型。采用外部 OIDC 时 Java 作为资源服务器校验 JWT；浏览器 SSE 的认证方式单独冻结。租户来自已验证成员关系，而非客户端声明。

**实现步骤**：

1. Java `SecurityConfiguration` 定义认证链和少量匿名路径；`AuthorizationService` 查询 tenant、membership、role_permission、resource_binding，默认拒绝。
2. 为创建、读取、取消、下载、流订阅分别建立权限点；资源查询通过“资源 ID + 租户 + 作用域”定位；建立跨租户与同租户不同成员测试。
3. Java 生成短期内部身份凭证，含 subject、tenant、scope、audience、expiry、policyVersion；覆盖不可信身份头。Python 新增内部凭证验证与范围检查，通过接口接收身份，不跨库查 Java 表。
4. 撤权时更新政策版本、失效授权缓存；长任务在危险步骤前重新确认权限；迁移前封住 Python 非授权直连入口。

**达到结果**：未认证返回 401；角色无权限返回 403 或按资源隐藏策略返回 404；修改请求头、猜测资源 ID、重连 SSE 都无法跨租户。该结果需要 Java 与 Python 的范围校验共同通过测试。

### J04～J05：共享速率与并发隔离

**实现功能**：约束租户请求速率，防止长连接、上传和评测挤占普通接口。

**设计**：`AdmissionService` 组合 Redis 共享速率限制和实例本地并发池；分为短请求、上传、SSE、评测四类资源，不用统一 QPS 代替资源限制。租户全局在途量另设租约策略，说明故障超额窗口。

**实现步骤**：Java 在受权后执行 Lua 原子扣速率预算；按路由模板选择 Semaphore/Bulkhead，另外限制等待者数量；失败返回 429 或 503，附 requestId 与 Retry-After。获取许可后通过 finally 或生命周期回调成对释放；SSE 许可覆盖整段连接。增加取消、异常、超时和实例重启场景验证。

**达到结果**：两个 Java 副本合用租户速率额度；慢 SSE 触顶时普通查询仍有独立容量；拒绝可观测，许可不随请求异常持续泄漏。Python 执行吞吐仍由 Worker 容量决定。

### J06：资源配额与实际用量结算

**实现功能**：限制租户预算、文件存储与任务数量，展示实际用量。

**设计**：Java `QuotaService` 管理 quota_account、quota_reservation、quota_ledger；预占、确认、释放、未知待对账是显式状态，唯一 settlementId 防重复结算。

**实现步骤**：提交前以条件更新或行锁在事务内扣可用额度并建预占；与提交台账建立唯一关联。Python 按 run/attempt/usageSequence 返回用量，Java 幂等结算；遗漏事件由对账任务查询补齐。运行中按预算上限停止继续调用，未提供用量的供应商标记估算值，不能伪装为实测。

**达到结果**：并发预占不超账面预算，同一用量不重复计入；超时未知任务不会被提前释放额度。若供应商和 Python 无法在调用前约束输出 Token，只能给软预算和超额容忍范围，不能宣称绝对硬限额。

### J07：任务提交幂等与双写恢复

**实现功能**：用户双击、网关超时重试不会创建多个相同任务。

**设计**：`ExecutionSubmissionService` 管理 submission 状态；数据库唯一约束保护并发，Java submissionId 是 Python 创建与查询的稳定键。

**实现步骤**：Java 事务写请求摘要和 pending 台账；调用 Python 创建接口并传 submissionId；Python 唯一约束去重。成功后保存 runId；响应丢失进入 unknown，由对账查询恢复，不立即释放配额。进程重启扫描未完成台账。若采用异步投递，台账与 Outbox 同事务写入。

**达到结果**：同键同参得到同一 runId，异参 409；在入队成功后断网再重试仍只有一个逻辑任务。外部工具副作用需另有幂等，不能由提交去重推导。

### J08：超时与取消

**实现功能**：请求卡住不会永久占用入口；用户可以显式取消后台任务。

**设计**：`RequestBudget` 区分普通调用截止、SSE 空闲、连接寿命和后台任务截止；浏览器断线与任务取消是两个不同事件。

**实现步骤**：Java 分类构造 HttpClient 调用预算，为流体读取及下游写入设计可关闭的超时机制；客户端断开时关闭上游 InputStream 并释放许可。受权取消 API 调用 Python 取消接口，展示 cancelling 直到权威终态确认；用慢响应头、无心跳、慢消费者测试验证，避免仅设置 request.timeout 即认为覆盖全流。

**达到结果**：超时后入口资源回收；断线后任务可以继续，显式取消后状态可查询；无法中断的外部调用如实展示取消边界。

### J09：观测与审计

**实现功能**：定位一轮 Agent 请求慢在哪里，追踪谁修改了配置或调用了危险工具。

**设计**：Java 用 Micrometer 记录治理指标；requestId/traceId 贯穿 HTTP、submission、run，审计记录主体、动作、资源、政策版本和结果。

**实现步骤**：过滤器生成或校验请求标识；应用服务在业务事务中写关键审计记录，异步出口用 Outbox；Python 接收 trace 上下文并在执行事件中关联。将低基数指标暴露给采集端，建设延迟、拒绝、池利用率、队列年龄面板；审计检索本身要授权、分页与脱敏。

**达到结果**：可以从 requestId 定位提交与执行，区分准入慢、排队慢、模型慢；权限与配置变更留痕。审计落库失败时，高危动作按策略拒绝或进入待处理，不能静默丢审计。

### J10：熔断与安全重试

**实现功能**：Python 或外部依赖故障时快速拒绝，恢复后逐步放量。

**设计**：Java `CapabilityCallPolicy` 按操作类别管理 Resilience4j 熔断及隔离；重试允许列表与业务幂等策略绑定。

**实现步骤**：在应用端口/网关调用处装配策略，过滤业务 4xx 与主动限流；只给可重放读取及已建立端到端幂等的提交配置重试，共用总截止和随机退避；半开限制试探量。流开始后不透明重试。模拟故障比例变化并观察开闭状态。

**达到结果**：依赖持续失败时不让大量请求长时间等待；恢复不会瞬间全量冲击；不会将拒绝或断线误报为依赖崩溃。

### J11：多副本与实例选择

**实现功能**：Java 可水平扩容，Python 请求分配能考虑实例负载。

**设计**：Java 不保存唯一业务状态；`PythonEndpointResolver` 保留发现过滤，增加选中实例的在途计数和失败隔离。初期可先轮询，确认偏载后启用负载策略。

**实现步骤**：登录会话、配额、台账放共享服务；为选中实例创建带释放方法的调用句柄，覆盖健康调用与流式调用生命周期；摘流实例停止接新请求，连接完成后再释放计数。计数是单 Java 实例视角，不当作全局精确负载；必要时结合 Python 容量信号。

**达到结果**：任一 Java 实例退出后其他副本可继续查询；长流场景偏载可被检测与缓解；全部下游不可用时快速 503。

### J12：SSE 订阅恢复

**实现功能**：刷新页面或实例切换后继续查看同一任务进度。

**设计**：提交与订阅分离，runId 不变；Python 持久事件是权威，Java 执行订阅授权和连接治理。

**实现步骤**：Java 校验 run 归属后转发游标和事件 ID；前端保存最后确认游标并去重。Python 返回稳定递增序列、终态及游标过期信号。对慢消费者采用有界缓冲或关闭连接，之后通过回放恢复；撤权后终止订阅需有明确时效。

**达到结果**：重连不会重新提交任务，重复事件不会重复更新界面；切换实例后可以恢复。历史已清理的游标返回明确重置协议，不静默漏事件。

### J13：共享执行与 Worker 容灾（Java 编排，Python 实施执行存储）

**实现功能**：任务在多主机 Worker 间分配，旧 Worker 不能覆盖恢复后的新状态。

**设计**：执行权威保留 Python；Java 只管理提交、授权恢复和状态投影，不创建另一套 Worker 队列。

**实现步骤**：Python 为现有队列端口新增 PostgreSQL 适配，覆盖领取、续租、写事件和完成；租约带 fencing token，所有状态变更校验持有者。Java 将恢复请求做受权操作并记录审计，状态以 Python 查询校准。SQLite 数据先停写迁移、核对数量与序列再切换，保留恢复方案。

**达到结果**：双 Worker 并发领取不双领，旧租约写回被拒绝；过期任务按失败或可恢复策略处理。此项不能只写 Java 完成。

### J14：文件与产物共享

**实现功能**：换实例仍可下载受权文档和生成产物。

**设计**：Java 管业务归属与下载资格，Python 管对象引用与内容生成；对象 key 不构成授权凭证。

**实现步骤**：Java `ArtifactAccessService` 校验资源绑定，通过内部 API 获取对象引用后流式下载或生成短期授权；Python 将文件写共享对象存储，隔离租户命名空间。撤权要求即时生效时用代理下载，签名 URL 则明确失效窗口；清理任务不得删除仍被引用对象。

**达到结果**：文件不依赖某个 API 实例本地目录，猜测 key 不能越权读取；到期访问被拒绝，既有引用可追踪。

### J15：缓存一致性

**实现功能**：降低重复权限/配置查询，同时避免撤权后长期保留访问能力。

**设计**：Java `PolicyCache` 缓存带版本的配置和授权结果，键包含租户与主体；关键操作可强制回源。

**实现步骤**：短 TTL、过期抖动、热点回源合并；写政策后更新版本并发布失效通知，通知丢失仍由短 TTL 收敛。撤权敏感路径比较权威版本或强读。不要缓存带私密内容的跨租户响应，也不为随机资源 ID 建无限负缓存。

**达到结果**：相同查询减少数据库访问；撤权在规定时效内生效；缓存不可用时仍执行正确权限判断。

### J16～J17：配置发布与基础设施容灾

**实现功能**：治理规则可安全变更，发布/依赖故障可恢复。

**设计**：Java `GovernanceConfigService` 管规则版本、校验和生效记录；运维方案明确数据库、Redis、Nacos 和对象存储的故障矩阵。

**实现步骤**：新配置先绑定类型并校验，再整份原子替换；记录版本与回滚目标，实例上报已应用版本。Nacos Discovery 与 Config 分开接入，不能认为现有发现依赖自动支持配置发布。发布时摘流排空；数据库执行兼容迁移、备份和恢复演练。切换 Redis 后计数丢失可能暂时超额，硬账本不能依赖它。

**达到结果**：非法规则不生效，实例配置差异可见；回滚有依据；报告实际 RPO/RTO 与影响范围，不以“部署了集群”代替恢复验证。

### J18～J19：公平调度与自适应容量

**实现功能**：批量任务不长期占满容量，负载变化时有序调整准入。

**设计**：Java 管租户准入权重及配额，Python Worker 管执行队列公平领取；按交互/批量划分服务等级，设置防饥饿策略。

**实现步骤**：先设置固定权重、租户队列上限与最长等待；Python 提供队列年龄/运行数信号。收集稳定基线后 Java 再按延迟与饱和度调整准入，上下界、冷却期和手动开关必须齐全；扩容动作交给部署平台，Java 输出指标而非自行拉起本机进程。

**达到结果**：大租户持续提交时小租户仍有执行机会；容量调节可解释、可回滚且无持续振荡。该项依赖真实负载数据，优先级 P2。

### J20：危险工具执行治理

**实现功能**：脚本、EXE、MCP 和 Skill 的高危行为必须受政策约束。

**设计**：Java 管可用目录、授权与审批，Python 在最终执行点强制检查并落实沙箱。

**实现步骤**：Java 为工具版本建立风险等级、允许参数范围、工作区/网络范围及 approvalPolicy；下发短期受限执行许可。Python 在执行前检查工具版本、参数摘要、作用域和有效期，高危请求走 J23 审批；沙箱限制进程、文件、出网和资源，真实凭据通过受控引用获取。

**达到结果**：绕过前端或由模型构造调用也不能越权，审批不能被挪用于另一组参数；Java 授权并不能替代执行机的操作系统隔离。

## 11. 结合当前项目新增的 10 项 Java 业务功能

以下功能在 Java 中当前尚未实现。对于已有 Python 能力，建设方式是迁移控制与业务政策、复用执行能力；切换期间必须保持单一写入方。

### J21：分布式定时任务中心（P1）

**项目依据与功能**：`python_backend/api/routers/schedules.py` 已有定时任务 CRUD、手动运行和 `create_schedule_runner`，按分钟间隔扫描后提交执行。Java 增加可跨副本协调的调度中心，支持时区、暂停、错过触发策略和执行记录。

**怎么设计**：Java `ScheduleService` 管计划，Quartz JDBC JobStore 管持久化触发和集群协调；计划只触发任务提交，Agent 继续由 Python Worker 执行。数据库保存 schedule、schedule_fire，`scheduleId + plannedFireTime + revision` 唯一；区分跳过、合并补一次、有限补跑，禁止无限补偿洪峰。

**怎么实现**：新增计划 API 与 Quartz Job；触发时生成稳定 submissionId，复用 J07/J06，不在调度线程执行模型调用。配置禁止并发或允许重叠的单计划政策；恢复时根据计划版本和时区计算。导入旧计划并保留 taskId 映射，停用 Python 旧扫描器后才启用 Java 触发器，切换期间记录水位。

**达到结果/验收**：双 Java 实例同一计划时刻只形成一个逻辑任务；重启不丢计划，错过的触发按明确规则处理；DST 和长任务重叠均有测试。Quartz 故障恢复仍依赖提交幂等，不承诺外部副作用恰好一次。

**参考**：[Quartz 集群机制](https://www.quartz-scheduler.org/documentation/quartz-2.3.0/configuration/ConfigJDBCJobStoreClustering.html)、[Spring Boot Quartz 集成](https://docs.spring.io/spring-boot/reference/io/quartz.html)。普通 `@Scheduled` 不能自动解决跨副本去重，参见 [Spring 调度文档](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)。依赖版本需按当前 Boot 单独验证。

### J22：评测驱动的发布门禁与灰度中心（P1）

**项目依据与功能**：已有 `api/routers/release.py` 的后台灰度观察、`evaluation.py` 与 `benchmarks.py` 的评测入口。Java 增加“评测通过才能发布”和稳定灰度决策，管理 Skill、模型策略及配置版本。

**怎么设计**：`ReleaseService` 管 draft → evaluating → approved → canary → active/rolled_back 状态，releaseId、被测版本摘要、数据集版本、阈值版本和报告摘要绑定；评测是事实输入，发布决策归 Java。

**怎么实现**：Java 创建评测申请，调用 Python 评测端口取得真实报告；校验目标版本和报告完整性，禁止用旧版本成绩给新版本放行。通过租户/工作区稳定哈希选择灰度队列，任务创建时冻结执行版本；观察窗口按最小样本量判断，样本不足保留观察。状态转移以 revision CAS，Java 多副本只能有一个有效决策；迁移后关闭 Python 原发布决策写入与观察动作。

**达到结果/验收**：评测未过不能上线；同一工作区稳定命中灰度版本；回滚影响新任务，旧任务保留原版本。重复评测回调和并发发布不会覆盖已生效状态，缺数据不能判成功。

### J23：人工审批与一次性执行许可（P1，高危工具对外前完成）

**项目依据与功能**：`api/routers/registry.py` 的 ToolPayload 已有 `approval_policy`，治理路由已有控制面。Java 将其变成可执行的审批流程，用于高危工具、发布或敏感导出。

**怎么设计**：`ApprovalService` 保存申请、申请人/审批人、资源与参数摘要、工具版本、权限版本、有效期；状态 pending → approved/rejected/expired/revoked，消费记录独立。审批通过不等于无限期拥有工具权限。

**怎么实现**：Python 在危险步骤前挂起并申请审批；Java 授权审批人，按政策禁止自批或要求复核。批准后签发与 operationId、参数摘要及受众绑定的许可；执行端向 Java 原子登记消费，再执行操作。消费响应丢失时按 operationId 查询，不能重新发起危险动作；已消费但执行未知则进入人工/幂等对账。外部调用必须用相同操作幂等键或补偿机制。

**达到结果/验收**：审批拒绝/过期后不会执行；修改参数、替换工具版本或重复使用许可被拒绝；审批与实际执行一一关联。许可一次性消费不代表外部副作用绝不重复。

### J24：模型路由与预算政策中心（P1）

**项目依据与功能**：`registry.py` 已有模型 provider、route、cost_policy 和 fallback_model_id 元数据。Java 将目录升级为租户级模型可用范围、用途路由、预算及回退政策。

**怎么设计**：`ModelPolicyService` 输出含版本的执行政策，按用途区分意图判定、生成、Embedding 和重排；回退必须保持能力、数据驻留与预算约束。模型实际调用仍在 Python。

**怎么实现**：Java 受权维护 model_policy、tenant_model_binding 和价格版本；校验回退环及不兼容能力。创建任务时生成许可模型集合、预算、最大回退次数和策略版本；Python 在每次真实调用前约束选择并上报用量。Java 不保存明文模型密钥，使用受控 credentialRef；不强制把内部每个 Token 流都绕回 Java。

**达到结果/验收**：租户无法调用未授权模型，失败只在允许集合内回退，不因回退突破预算；用量可关联到价格和政策版本。目录里标记 available 不能代替真实探测结果。

### J25：工作区与会话协作管理（P1）

**项目依据与功能**：已有工作区导入路由、会话路径与上下文范围绑定。Java 提供成员邀请、共享可见范围、会话归属和版本冲突处理。

**怎么设计**：`WorkspaceService`、`ConversationService` 管业务元数据与 ACL；Python 管上下文、历史和执行绑定。工作区成员关系与资源分享分开，不能因知道会话 ID 自动继承权限。

**怎么实现**：Java 建 workspace、workspace_member、conversation_binding、share_grant；保留历史 ID 并建立映射。修改成员与描述使用 revision CAS，旧 revision 返回 409；分享授权有有效期、范围和撤销入口。Python 创建/读取上下文时接收可信作用域，Java 不能直接改 Python 历史表。工作区文件路径授权与导入配额沿用资源政策。

**达到结果/验收**：成员可以在授权工作区协作，其他工作区不可见；并发编辑不会静默覆盖；撤销分享后新的读、订阅和下载被阻止。

### J26：统一任务查询与运营读模型（P1）

**项目依据与功能**：现有执行、评测、定时任务入口分散。Java 提供按用户、工作区、来源、时间和状态查询的任务中心，支持分页与批量取消申请。

**怎么设计**：`RunQueryService` 维护受租户隔离的 run_projection；投影服务查询，Python 是运行状态权威。主键关联 submissionId/runId，事件带 eventId 与版本，避免将旧事件覆盖新状态。

**怎么实现**：先用有界增量拉取与游标对账接入，不强制立即建设消息总线；Java 更新投影时比较版本并记消费水位。列表采用稳定排序与游标分页；详情必要时回源，展示 lastSyncedAt/是否陈旧。批量取消逐个鉴权并返回逐项结果，不能跨租户批量操作。

**达到结果/验收**：一个页面可查交互、定时与评测任务；事件重复、乱序和暂时断链后能收敛；投影滞后不会伪装为最新执行状态。UI 所需业务状态可由 Java 聚合，但不夺取执行权威。

### J27：外部应用 API Key 与机器身份（P2，有外部集成需求再做）

**项目依据与功能**：现有统一入口可扩展为供其他应用提交任务的开放接口；新增机器身份，无需复用个人长期登录令牌。

**怎么设计**：`ApiClientService` 管 tenant、clientId、scope、允许工作区、额度与失效时间；Key 只展示一次，数据库保存不可逆摘要及安全前缀，认证后映射成与人类身份同结构的主体。

**怎么实现**：Java 新增申请、轮换、撤销与调用记录 API；使用安全随机数生成 Key，校验时避免明文日志和弱哈希；新旧 Key 可短暂重叠。调用同时受租户及客户端限流，禁止客户端自选未授权 tenant/workspace；Python 只接收受限内部身份。

**达到结果/验收**：外部应用只能调用授权动作，撤销后在规定时效内拒绝；轮换不必停服务；Key 无法通过管理查询再次导出。此 Key 不与现有用户模型凭据混用。

### J28：任务完成通知与 Webhook（P2）

**项目依据与功能**：独立 Worker 的长任务不应要求用户一直保持 SSE。Java 提供站内通知，并在明确配置后向外部系统发送终态通知。

**怎么设计**：`NotificationService` 监听稳定终态事实，站内 notification 和 webhook_delivery 独立；按 eventId + subscriptionId 去重，至少一次投递，接收方也要幂等。

**怎么实现**：终态投影更新时同事务写通知 Outbox；受权创建订阅，投递使用签名、时间戳与 deliveryId，限时响应与指数退避，超过次数进入失败列表。配置出网目标时防 SSRF，校验解析 IP、跳转和 DNS 变化，阻断云元数据/回环/内网等未授权目标；优先白名单目标。实际地址和签名凭据保持私密配置，不进入仓库。

**达到结果/验收**：关闭浏览器仍可收到任务完成状态；投递失败不影响任务终态，可查询/重投；恶意 URL 不能借通知访问服务内部资源。本次只写设计，不发送任何消息。

### J29：数据保留、删除与清理编排（P1）

**项目依据与功能**：会话、记忆、向量、执行事件与对象存储涉及多个模块。Java 提供受权的删除申请、保留政策与清理进度，避免只删业务目录而内容仍可检索。

**怎么设计**：`RetentionService` 管 deletion_request 和各模块清理回执；先墓碑/停止新访问，再按依赖顺序清理，状态 requested → blocked → purging → completed/failed。共享内容按引用关系判断，不能直接删被其他资源使用的对象。

**怎么实现**：Java 冻结作用域、撤销分享并取消或隔离相关在途运行；通过 Python 模块 API 分别清理记忆、检索、文件、产物与事件。各步骤使用删除请求 ID 幂等，失败重试可查看，禁止直接跨库删表。清理完检查可访问性和引用；备份到期策略独立记录，保留最小必要审计且脱敏。

**达到结果/验收**：删除申请后新请求不能读回内容；各存储清理有回执，部分失败可恢复；备份尚未到期时不得宣称所有副本已物理擦除。

### J30：配额与治理管理台（P1）

**项目依据与功能**：已有 Harness、settings、observability 与评测界面，Java 新增可管理的治理 API，前端在现有控制台呈现租户预算、拒绝原因、池容量、策略差异与审批队列。

**怎么设计**：Java `GovernanceAdminService` 聚合 J04/J06/J09/J16 的权威数据；只读查看与规则修改分别授权，规则使用 revision 和版本发布。此项复用已有治理能力，不创建第二套计数和账本。

**怎么实现**：提供分页查询和带时间范围的统计 API；策略编辑先校验/预览影响，再提交版本，记录操作人与变更摘要。区分配额拒绝、系统过载、依赖故障及凭据错误，界面展示安全原因；前端按根 DESIGN.md 接入。规则发布失败展示各实例应用状态，不能仅凭数据库保存成功显示全局生效。

**达到结果/验收**：管理员能定位某租户被拒绝的原因、调整合法限额并追踪生效；普通用户只见自己的用量；并发修改返回冲突而非互相覆盖。

## 12. 与旧方案的衔接和开发交付要求

已回看 [架构迁移草案](微服务架构迁移草案.md) 的领域所有权、幂等、队列、SSE 和迁移章节，以及 [第二阶段能力设计](stage-two-capability-design.md) 的权限、成本、一致性与门禁主题。本文细化 Java 实现任务；检索重排、记忆冲突、Embedding 流水线仍属于 Python 能力建设，不迁成 Java 来凑技术项。

| 既有能力 | 迁移后唯一权威 | 兼容与切换要求 |
| --- | --- | --- |
| Python schedules 计划与扫描 | Java 计划和触发记录；Python 执行 | 导入计划、冻结旧扫描、确认最后触发水位再启用新调度 |
| Python release 灰度观察和决策 | Java 发布政策与状态；Python 评测事实和版本执行 | 导入政策并停止旧决策写入，禁止双观察器同时推进状态 |
| Python registry 模型/工具目录政策 | Java 授权目录、风险和路由政策；Python 协议及执行适配 | 先加政策版本读取接口，再切换管理写入；运行中版本保持稳定 |
| profile/settings 与模型凭据 | 按用户业务配置、运行时配置、凭据引用分别明确拥有方 | Java 不复制运行私钥或真实服务地址到可提交配置；凭据迁移单独设计 |
| 任务状态与事件 | Python 权威；Java 查询投影 | 依靠稳定 ID、事件版本和对账，不通过双写两份权威状态实现同步 |

**建议开发批次**：先做 J01～J09 与必要的端到端身份/幂等配合，再做 J30 管理入口；第二批完成 J10～J17、J20、J23～J26、J29；定时需求明确时加入 J21，发布链成熟后加入 J22；J18/J19/J27/J28 根据实际负载及外部集成需要推进。不因清单有 30 项就一次全部开工。

每个功能开发交付必须包含：Java 接口与应用用例、表结构/迁移、Python 契约变更、前端入口（需要时）、错误与故障状态、至少一个成功和一个关键失败场景、实际验证结果。需要停旧实现的功能必须附切换与回滚步骤。

结果表述按证据填写：“已实现接口”与“已通过双副本/故障演练”分开记录。本文没有执行上述功能，不以设计目标冒充当前能力；新增官方资料只用于机制参考，兼容版本仍需实施前验证。
