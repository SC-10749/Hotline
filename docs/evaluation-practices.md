# 顶级高星项目的评测是怎么做的

> 更新日期：2026-11-23
> 目的：看清生态里最成熟的项目**怎么把评测做进工程**，再决定我们抄哪几条。
> star 用「量级」表述（社区公开数值，非当日实测）；当日实测值见 [差距清单](evaluation-gap-analysis.md) 文末。

## 一、要看的是三类项目，不只是评测框架

| 类别 | 代表项目（量级） | 它们的评测在解决什么 |
| --- | --- | --- |
| ① 评测平台 | Inspect AI（3k+）、promptfoo（27k+）、Opik（20k+）、Phoenix（12k+）、Langfuse、MLflow、deepeval（19k+） | 怎么判、怎么批量跑、怎么看结果 |
| ② 用评测做产品的超级项目 | LangChain / LangGraph（10万+ / 2万+）、Dify（7万+）、RAGFlow（6万+）、OpenHands（6万+）、browser-use（6万+）、Open WebUI、n8n、LlamaIndex（4万+） | 怎么把「改一版就回归」变成日常动作 |
| ③ 基准与研究 | lm-evaluation-harness、SWE-bench（6k+）、Toolathlon、BFCL、τ-bench、Arena-Hard / AlpacaEval、METR RE-Bench、DSPy（3万+）、OpenAI Evals（19k+） | 怎么定义「难任务」与「可信判定」 |

第 ② 类最值得抄——它们的评测不是研究附属品，而是产品的日常回路。

## 二、十个被反复验证的做法

### 1. 评轨迹，不只评终答

- **谁在做**：LangChain / LangGraph 的 trajectory evaluator、OpenHands 的 trace 分析。
- **怎么做**：把中间步骤（思考、工具调用、状态变化）与最终答案一起交给评委，判「过程是否高效、是否走错路」。理由很直接：终答对但过程跳过校验，是最危险的一类错。
- **我们**：已经有结构化轨迹断言（澄清数、工具、步骤、轮数），但**没有语义化的轨迹评分**——只能验「做过」，验不了「做对」。
- **抄**：S-005 里加一条「语义轨迹评分」，与参数级工具断言一起做。

### 2. 每条用例单独判定，并统计「可评覆盖率」

- **谁在做**：Dify 的评测台最典型——每条用例判 Pass / Fail / Not gradable / Untested，汇总给「通过率 + 覆盖率」。
- **为什么重要**：通过率高但覆盖率低（比如一半用例没被判分）是自欺欺人。
- **我们**：现在 `passRate` 分母是「已执行且已评分」的样本，被预算跳过/未评分的样本口径混乱（这轮刚修过一次）。
- **抄**：S-006 加 `gradableCoverage`（可评覆盖率）与 `notGraded` 计数，和通过率并列展示。

### 3. 检索与生成分开评，且切片方式必须与主链一致

- **谁在做**：RAGFlow、GraphRAG（local/global 两阶段分别评）、LightRAG、RAGAS 生态。
- **怎么做**：召回侧看 Recall@k / MRR / 命中率，生成侧看忠实度与答案相关性；**两边用同一份切片**。
- **我们**：Ragas 跑在 `eval/` 独立脚本里，切片方式与主链不同（我们自己在 `docs/evaluation.md` 里承认这是「理想化切片」），且报告与 Agent 测评报告分离。
- **抄**：把检索指标并进同一份运行报告，标出切片口径差异。

### 4. 数据集 + 人工标注 + 批量对比是一条闭环

- **谁在做**：Dify（标注 → 批量测试 → 模型/参数对比）、OpenAI Evals（few-shot 人工示例做 model-graded 基准）。
- **怎么做**：标注是一等公民，不是副产品；有了标注集才能批量对比不同模型/不同参数版本。
- **我们**：样本全手写，没有「标注—回流—回归集」的闭环。
- **抄**：S-007 里加「人工标注回流」，与自动合成并列。

### 5. harness 与 agent 解耦：环境、判定归 harness，agent 只负责产出

- **谁在做**：OpenHands、SWE-bench、Toolathlon（108 个长程任务、32 个真实应用、604 个工具，多为 MCP，**每个任务独立容器**，平均约 20 轮工具调用）、browser-use（真实系统搬进 Docker 的 SaaS-Bench 一类做法）。
- **怎么做**：判定脚本独立于被测系统，跑在固定环境里，产出可复现的通过/失败判定。
- **我们**：判定逻辑与执行都在测评模块内，跑的是真实 Worker，判定与被测环境没有隔离。
- **抄**：S-008（沙箱）+ S-009（任务集）。

### 6. 任务配置化 + 结果快照 + 基线对比 + 定期回归

- **谁在做**：lm-evaluation-harness（YAML 任务、`--tasks`、结果落 JSON 可与上次比）、vLLM / Transformers（固定模型 revision、结果文件进版本库、nightly 回归）。
- **怎么做**：配置、结果、基线三者都版本化，回归靠定期重跑 + 与基线 diff。
- **我们**：有 snapshot（样本正文 + sha256）和 provenance（commit/技能 sha/模型），但**样本改动没有 diff 视图**，也没有定期回归机制。
- **抄**：S-006 里的「与基线逐样本 diff」升级成「基线矩阵 + 定期回归任务」。

### 7. 相对评测：同一道题两版答案谁更好，并做长度去偏

- **谁在做**：Arena-Hard、AlpacaEval、Chatbot Arena、MT-Bench。
- **怎么做**：不设绝对阈值，而是让评委在同题的两版答案间择优；AlpacaEval 专门做**长度去偏**，否则长答案天然占便宜。
- **我们**：只有绝对阈值门禁（passRate ≥ x）。
- **抄**：S-006 加「同题择优」判定，并在展示里标注长度差，避免误判为质量提升。

### 8. 评委可换，指标驱动优化

- **谁在做**：JudgeArena（评委模型/来源可换）、DSPy（metric + optimizer：定义指标后自动优化 prompt 或程序）、OpenAI Evals（grader 可自定义）。
- **怎么做**：评委是配置项而不是写死的；评测结果按评委分组，用来发现「换个评委结论就变」的噪声。
- **我们**：判分模型固定走 `config.settings`，没有任何一致性度量。
- **抄**：S-005 已写入 `judgeModelId`（找不到就判 `invalid_rubric`，不静默换评委）。

### 9. trace 是一等公民：离线跑批 + 在线评测共用一套数据

- **谁在做**：Phoenix（预置 hallucination / relevance / toxicity / QA correctness 的 LLM-as-judge 模板 + experiment tracker）、Opik（online eval：对生产 trace 跑规则）、Langfuse。
- **怎么做**：同一条 trace 既能离线重放评，也能挂在线规则做持续监控。
- **我们**：只有离线跑批，没有在线评估；事件流也没有 OpenTelemetry 出口。
- **抄**：S-010（候选）。

### 10. 质量断言长在流水线里，失败即阻断

- **谁在做**：Airflow 的 data quality check、Dagster 的 asset checks、Prefect 的 task assertion、n8n 的工作流校验。
- **怎么做**：断言写在流水线里而不是另开一个「质量平台」，红了就挡住下游。
- **我们**：有 `python -m python_backend.eval_gate` 退出码，但仓库没有 CI workflow，等于没有接进流水线。
- **抄**：S-008 加 GitHub Actions。

### 附：自主时长（METR / RE-Bench）

「能连续自主工作多久」是个新指标维度（50% 任务完成时长）。对现在的 Hotline 还太远，但当样本变成多轮长任务时，它比「平均轮数」更有意义——先记进路线图尾部。

## 三、他们怎么做 vs 我们怎么做

| 环节 | 顶级做法 | 我们现在 | 差距 |
| --- | --- | --- | --- |
| 判分 | 组件级指标库 + 评委可换 + 相对择优 | 一条通用 model 通道 + 结构断言 | 缺语义指标库与评委可配（S-005） |
| 过程 | 语义轨迹评分 | 结构轨迹断言 | 缺过程语义（S-005） |
| 统计 | 通过率 + 可评覆盖率 + 基线 diff + 定期回归 | 通过率 + passAtK/flakyRate + 两两 run 对比 | 缺覆盖率与回归机制（S-006） |
| 样本 | 自动合成 + 人工标注回流 | 全手写 | 缺（S-007） |
| 执行 | 容器沙箱 + 官方判定脚本 | 真实 Worker + `eval:` 命名空间 | 缺（S-008 / S-009） |
| 接入 | 断言长在流水线（CI） | 有 CLI 无 CI | 缺（S-008） |
| 线上 | 生产 trace 上持续评测 | 只有离线跑批 | 缺（S-010 候选） |
| 检索 | 与主链同切片的召回指标 | 独立脚本、理想化切片、报告分离 | 缺 |

## 四、我们该抄的，按顺序

1. **S-005**：语义指标 + 参数级工具断言 + 评委可配 + 语义轨迹评分（抄做法 1、8）。
2. **S-006**：可评覆盖率 + 同题择优 + 基线矩阵 + 定期回归（抄做法 2、6、7）。
3. **S-007**：样本自动合成 + 人工标注回流 + 红队与多维风险（抄做法 4，加上安全维度）。
4. **S-008**：容器沙箱 + 官方判定脚本 + CI 流水线 + 成本汇总（抄做法 5、10）。
5. **S-009**：任务集注册表 + 长程工具任务模板（Toolathlon / BFCL 风格）。
6. **S-010（候选）**：在线评估 + OTel 出口（抄做法 9）。
7. **检索指标并表**：把召回指标与 Agent 样本结果并进同一份报告，并标明切片口径差异（抄做法 3）。

抄的顺序原则：**先让判定可信，再让样本够多，最后才谈在线化**。

哪些顶级项目可以直接接进我们、怎么接、代价多大，见 [顶级项目哪些能接进 Hotline](evaluation-integration-options.md)。
