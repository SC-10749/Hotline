# 简历写作规范

> 本 skill 是「怎么写」的约束，不是「写什么」的清单。写哪个项目、面向什么岗位，由用户或任务指定。
> 上游原文在 `references/`，来源、许可与刷新记录见 `PROVENANCE.md`。

## 何时使用

- 写、改任何简历类文档（`docs/简历.md`、`F:\简历\简历.md` 或用户指定路径）。
- 把项目经历、工作经历改写成简历条目。

## 工作流

1. **确认范围**：目标岗位（决定技术栈与要点排序）、写哪些项目、篇幅。不清楚就先问，不要默认全量展开。
2. **取证**：从代码、测试、提交记录、文档里拿事实——文件数、代码行数、模块数、接口数、并发数、实测数据、修复过的真实缺陷。**没有证据的数字一律不写。**
3. **定结构**：按目标岗位的优先级排章节；技术岗位用 ATS 通用标题：技术栈 / 项目经历 / 工作经历 / 教育背景 / 技能。
4. **写要点**：按下面的 X-Y-Z 句式逐条写，先结论后机制。
5. **自检**：跑下面的自检清单，逐条对照；不通过就改。
6. **交付**：写进目标文件并回报改了哪些地方、哪些数字有据可查、哪些是定性表述。

## 硬规则

1. **句式（X-Y-Z）**：`达成了 X（用 Y 衡量），通过 Z`。X 是结果，Y 是尺度，Z 是你的动作与机制。
   - 差：负责执行队列与工具治理。→ 好：重构执行队列为 slot 维度放行，把「同会话只允许一个活跃运行」扩展为单会话 8 路并行实测全绿（Redis 模式 8 Worker 同秒起止、零锁残留）。
2. **顺序**：先结论后机制；每条 ≤ 2 行（中文约 70-90 字），一个项目 4-6 条，别堆 9 条。
3. **动词**：用强动词开头（构建、落地、重构、优化、驱动、压缩、收敛、修复、量化），不用「负责 / 参与 / 协助」这类职责词开头。
4. **量化优先**：能量化就量化（规模、吞吐、耗时、覆盖率、缺陷数、实测并发数）。**没有真实数据时不要编**：改用可核对的规模事实（文件数、行数、模块数、接口数），或明说「定性」并给出会改变结论的指标。
5. **技术栈分组**：语言 / 框架与运行时 / 数据库与存储 / 中间件与协议 / 工具链；ATS 按关键词匹配，缩写与全称都要出现（如 PostgreSQL、pgvector、RAG、MCP、SSE）。
6. **ATS 硬约束**（面向 ATS 投递时必须满足）：
   - 纯文本 Markdown，不用表格、多栏、文本框、图片承载信息。
   - 章节标题用通用词，不自造说法。
   - 日期格式统一（`2026.10` 这种 YYYY.MM）。
   - 不用特殊符号当项目符号。
7. **真实性**：不写没做过的事、不虚构规模与影响；「我做的」与「团队做的」要分清。
8. **可追问**：每条要点都要能展开讲两分钟——写不出细节的条目说明它还不够具体。
9. **篇幅**：一个项目 ≤ 1 页；整份优先 1 页；超了就删要点，不要缩字号。
10. **去水分**：删掉所有不能被追问的形容词（高效、强大、丰富、良好）。

## 自检清单

- [ ] 每条要点都有可核对的数字或明确的技术事实
- [ ] 每条都符合 X-Y-Z，动词够强，没有「负责 / 参与」开头
- [ ] 一个项目 4-6 条，每条 ≤ 2 行
- [ ] 技术栈按分组列出，ATS 关键词齐全
- [ ] 没有表格 / 多栏 / 图片 / 特殊符号
- [ ] 日期格式统一
- [ ] 通篇没有编造的指标
- [ ] 每条都能被追问出实现细节
- [ ] 篇幅符合要求
