# 需求诊断手册

SKILL.md 里的五个状态在这里展开：怎么认出来、问什么、怎么动手纠正。

## 诊断流程

1. 读用户的原话，找出症状属于哪个状态。
2. 从**最早**的状态开始处理。R0 没解决就去问 R2，等于在错误的地基上盖楼。
3. 当前状态的"验证指标"全部满足，才允许进入下一个状态。
4. 每处理完一个状态，把结论落进对应的产出物（问题陈述简报、需求层级、约束清单、范围定义）。
5. 用户跳过某个状态时，指出跳过会带来的风险，仍然按流程走，不要装作已经过。

## R0 只有方案没有问题

**症状**：开口就是"我要做一个 X"；说不清谁在受什么苦；列了一堆功能但说不出为什么；"大家都需要"；在抄别家的产品。

**关键问题**
- 不做这个东西会怎样？
- 谁在痛？具体是谁（"用户"不算，"每天处理 200 单的客服"才算）。
- 他们今天是怎么解决的？痛在哪一步？
- 什么触发了你现在想这件事？以前为什么不解决？

**干预手法**
- JTBD 自述："当【情境】时，我想要【动机】，以便【结果】"，让用户自己填，不要替他编。
- 五个用户测试：点名五个具体受益者（可以只有一个是自己）。
- 问题考古：把这个想法追回到某一次具体的难受瞬间。

**产出物**：问题陈述简报（含"明确不解决什么"）。

**验证指标**：问题陈述里没有技术词；能讲给不了解这个项目的人听；成功标准可判定。

## R1 方案先行

**症状**：需求写成实现（"需要一张 users 表""要用 Redis 缓存"）；离开技术就说不清需求；被问"为什么"时只能答"因为大家都这么做"。

**关键问题**
- 如果这个技术不存在，你需要什么结果？
- 这项技术是硬约束（合规/既有系统/合同），还是你只会这个？
- 你在解决自己的问题，还是在抄别人的方案？

**干预手法**
- 功能抽取：把每条需求改写成"系统必须【动词】…"，去掉所有技术词。
- 去掉方案重述：用完全不涉及实现的方式描述需求，让用户自己认出被抽掉的部分。
- 约束与偏好区分：把"必须用 X"分到真实约束或偏好两栏。

**产出物**：改写后的需求句、约束栏里的技术项。

**验证指标**：每条需求都能换一种实现方式满足。

## R2 需求含糊

**症状**："用户应该能…"没有具体对象；形容词需求（快、易用、现代、友好）；写不出验收标准；说不清"做完了"长什么样。

**关键问题**
- 怎么知道这条需求被满足了？
- 最小满足是什么样？
- 给一个具体例子：上一次真实发生是什么样子？
- 什么样的实现会让你失望？什么样会让你满意？

**干预手法**
- 具体度阶梯：谁（具体角色）→ 在什么场景 → 做什么（具体动作）→ 得到什么（具体结果）。
- 验收场景：Given X，When Y，Then Z，每条需求至少一个正常场景加一个边界场景。
- "Done 看起来像"：用一句可观察的事实描述完成状态。

**产出物**：用户故事 + FR/NFR/SC。

**验证指标**：每条需求都有编号和可判定的验收标准。

## R3 隐藏约束

**症状**：把假设当事实；没有依赖清单；实现到一半才发现"哦我忘了说…"；上线才发现数据量撑不住。

**关键问题**
- 这个上下文里什么是一定为真的？
- 你只是相信为真的有哪些？
- 如果它是假的，会怎么死？
- 你实际有多少时间、技能、预算？
- 依赖哪些外部系统？谁负责？

**干预手法**
- 约束清单：时间、预算、技能、基础设施、必须对接的系统、必须不动的系统。
- 假设映射：每条假设写"如果错了会怎样""怎么验证""谁来定""状态"。
- 失败预演：假设六个月后项目失败了，写出最可能的三个原因和缓解动作。
- 依赖盘点：哪些东西必须先存在。

**产出物**：约束清单 + 假设映射 + 失败预演。

**验证指标**：事实与假设分区清楚，每条假设都有验证方式。

## R4 范围蔓延

**症状**："顺便加个…"；分不出核心和锦上添花；每条都同等重要；范围只增不减。

**关键问题**
- 最小可用是什么？
- 如果只能上线三件，砍到只剩三件还成立吗？
- 什么条件下会重新考虑延后项？

**干预手法**
- MoSCoW：Must / Should / Could / Won't，Won't 要写理由防范围蔓延。
- 行走骨架：找出最薄但有用的版本。
- 强制排序：严格排序、不允许并列。
- 砍掉再加回：从全空开始，只加回必需项。

**产出物**：V1 范围定义（做什么、不做什么、延后项与触发条件）。

**验证指标**：V1 边界明确，延后项都有重新考虑条件。

## 六个反模式

| 反模式 | 表现 | 修法 |
| --- | --- | --- |
| 解决方案规格化 | 需求写成了实现 | 逐条问"换种实现方式也能满足吗"，能就说明抓到的是实现不是需求 |
| 干系人虚构 | 替不存在的用户想象需求 | 自己就是用户时诚实写自己的痛点；为别人做就去找证据或类比证据，不要编 |
| 无穷待办 | 所有需求一样重要 | 强制排序：只能上线一件是哪件？然后两件？三件？ |
| 过早精确 | 没人验证要什么就先定细节 | 需要精确的地方和可以 TBD 的地方分开，标"TBD，X 验证后确定" |
| 约束盲区 | 不盘点约束，撞墙了才知道 | 先列约束再谈需求，时间和依赖最先列 |
| 功能移植 | 抄别人的功能，说不出在自己场景里解决什么 | 逐条问"它在我的场景里解决什么问题"，答不出就砍掉 |

## 健康检查

分析过程中随时自问：

1. 我描述的是问题还是方案？
2. 不了解这个项目的人能听懂我的需求吗？
3. 我怎么测试这条需求是否被满足？
4. 我做了哪些还没验证的假设？
5. 按我的实际约束，这个范围做得完吗？
6. 明确不做什么的部分写了吗？
7. 我是在解决我需要的东西，还是在解决我只会做的东西？
8. 如果失败了，最可能的原因是什么？
