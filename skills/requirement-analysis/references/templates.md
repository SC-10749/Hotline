# 需求条目模板

复制下面的骨架填写。占位说明写在尖括号里，输出前删掉。

对话中不必原样输出这里的骨架：先给结论再展开，正式归档时再按模板写全。

## 问题陈述简报

```
问题陈述：[项目名]

[问题]
- 谁：[具体角色，"用户"不算]
- 什么问题：[他现在的处境和痛点]
- 影响：[因此发生了什么后果]

[现状]
- 现在怎么解决：[当前做法或绕路方式]
- 为什么不够：[差在哪一步]

[成功长什么样]
- [可判定的成功事实 1]
- [可判定的成功事实 2]

[明确不解决什么]
- [看起来相关但本版不碰的问题]
```

## 需求层级

```
核心需求（Must：缺了问题就没解决）
- [需求描述，从动词开始]
  - 缺了会怎样：[失败的影响]
  - 怎么验证：[可判定的检查方式]
  - 最小满足形态：[最薄的可接受实现]

支撑需求（Should：重要但有临时替代方案）
- [需求描述]
  - 价值：[带来什么]
  - 依赖：[必须先有哪条核心需求]
  - 升级为 Must 的条件：[什么情况下必须提前做]

增强需求（Could：锦上添花，不阻塞 V1）
- [需求描述]

本版明确不做（Won't）
- [需求描述] —— 原因：[排除理由]
  - 重新考虑条件：[什么信号出现时重新讨论]
```

## 用户故事

```
### 用户故事 <编号> —— <标题>（<P1|P2|P3>）

作为<角色>，我希望<动作>，以便<价值>。

为什么是这个优先级：<价值>
独立验收：<单独实现它也能验证什么>

验收场景：
1. Given <前置状态>，When <动作>，Then <预期结果>
2. Given <边界状态>，When <动作>，Then <预期结果>
```

故事要过 INVEST：独立、可协商、有价值、可估算、小、可测。做不到就拆开。

## 功能需求

```
- FR-<编号>：系统 MUST <可验证的行为>
```

写不清的地方显式标注，不要自己填默认值：

```
- FR-<编号>：系统 MUST <行为> [NEEDS CLARIFICATION: <缺什么>]
```

## 非功能需求

```
- NFR-<编号>：<可度量指标>（<测量条件>）
```

用指标，不用"快""稳"。延迟写 P95/P99，并发和数据量写进括号。

## 成功标准

```
- SC-<编号>：<技术无关、可度量的结果>
```

```
| 假设 | 如果错了会怎样 | 怎么验证 | 谁来定 | 状态 |
| --- | --- | --- | --- | --- |

```
