# 需求交付前自检清单

逐条核对，任何一条不通过就回去改。

## 覆盖度

| 维度 | 必须覆盖的要点 |
| --- | --- |
| 功能范围与行为 | 核心目标、成功标准、明确不做什么、用户角色区分 |
| 领域与数据模型 | 实体与属性、唯一性规则、生命周期状态流转、数据量级 |
| 交互与流程 | 关键用户路径、错误态/空态/加载态、无障碍与本地化 |
| 非功能质量属性 | 性能延迟与吞吐、可扩展性、安全、可观测性、可维护性 |
| 约束与假设 | 期限、预算、合规、既有系统依赖、必须保持不变的既有行为 |
| 集成与依赖 | 上下游系统、第三方服务、数据同步方式、失败降级策略 |

## 状态推进条件

| 状态 | 通过条件 |
| --- | --- |
| R0 只有方案没有问题 | 问题陈述无技术词、能讲给外人听、成功标准可判定 |
| R1 方案先行 | 每条需求换一种实现方式也能满足 |
| R2 需求含糊 | 每条需求有编号、有 Given/When/Then 验收标准 |
| R3 隐藏约束 | 事实与假设分区清楚，每条假设有验证方式，失败预演写了三条 |
| R4 范围蔓延 | V1 边界明确，延后项都有重新考虑条件 |

## 模糊词扫描

正文出现下面任何词，都必须换成可判定的表述，或标注 NEEDS CLARIFICATION。

| 出现的词 | 改写成 |
| --- | --- |
| should、可能、最好 | 必选还是可选，不做会怎样 |
| 等等、之类、若干 | 具体包含哪些，边界在哪 |
| 合适、适当、合理 | 用什么标准判断，给一个具体例子 |
| 用户友好、简单易用 | 具体哪一步容易卡住 |
| 快、实时、流畅 | P50/P95/P99 延迟上限，并发量 |
| 可扩展、支持大量 | 用户数、QPS、数据量 |
| 安全、可靠 | 威胁模型，丢一条数据能否接受 |

## 反模式检查

- [ ] 没有把实现写成需求（"用 X"不是需求，是约束或偏好）
- [ ] 没有替不存在的用户想象需求
- [ ] 需求有强制排序，不是所有东西一样重要
- [ ] 还没验证的地方写成 TBD，而不是提前精确
- [ ] 真实约束在写需求之前就盘过一遍
- [ ] 抄来的功能都讲得清在自己场景里解决什么问题

## 健康检查

- [ ] 描述的是问题而不是方案
- [ ] 不了解项目的人能听懂
- [ ] 每条需求都能说出怎么测
- [ ] 列出了还没验证的假设
- [ ] 范围在真实约束下做得完
- [ ] 写了明确不做什么
- [ ] 想到了失败最可能的原因

## 交付门槛

1. 每条需求都有编号和验收标准。
2. 每条验收标准都是 Given/When/Then，且结果可判定真假。
3. 没有残留模糊词。
4. 每个用户故事都能独立测试、独立交付。
5. 写明本版不做什么。
6. 所有猜测的地方标了假设或 NEEDS CLARIFICATION，没有伪装成事实。
7. 追踪矩阵覆盖全部需求：既没有孤儿需求，也没有无来源需求。
8. 硬冲突已当轮指出，没有藏进待办。
9. 约束清单区分事实与假设，失败预演写了最可能的三个原因。
