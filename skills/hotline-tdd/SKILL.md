# Hotline TDD

## 什么时候用

- 手上已有一份需求条目（FR / NFR / 验收标准），要把它变成测试。
- 要改行为或修缺陷，需要先有失败测试再改实现。

需求条目本身说不清时，回到需求分析助手澄清，不要自己补默认值。

## 输入

需求条目由需求分析助手产出，会随会话交接过来。每条至少要有：触发输入、预期输出或状态、怎么验证。缺哪一条就问哪一条，别猜。

条目可能还是草稿：带 `NEEDS CLARIFICATION` 或未决问题的条目，说明它还没定。已定稿的条目照样先出测试清单（标注它来自哪条 FR/SC），未定稿的条目单独列成「待确认」清单，不要自己补默认值，也不要因为草稿就说没拿到需求。

## 流程

1. **列测试清单**：每条验收条件对应一个测试，写清测试文件、用例名、断言什么。清单先给用户看，别直接开始写代码。
2. **RED**：一次只跑一个测试，确认它因功能缺失而失败。失败原因分四类：
   - 断言因功能缺失而失败 → 进 GREEN。
   - 测试自身写错（导入、语法、夹具、断言）→ 修测试，再跑同一个。
   - 外部服务、网络、凭据不可用 → 隔离这个边界，不算产品行为失败。
   - 与本次无关的基线失败 → 记录下来，不借机重构。

   没按预期失败就不要开始写实现。
3. **GREEN**：只写让当前测试通过的最小实现，不顺手加范围外的功能。
4. **交付检查**：按仓库根目录 `AGENTS.md` 规定的命令跑，并如实报告哪些是行为测试、哪些只是构建检查。
5. **报告**：实现了什么、RED/GREEN 证据、跑了哪些命令、哪些没跑、有什么风险。

## 仓库现实

- 后端没有声明 pytest：用标准库 `unittest`，沿用现有测试布局。
- 前端没有独立测试脚本：`npm --prefix frontend run build` 只是构建检查，交互行为要人工验证并写下来。
- 测试不得连真实大模型、数据库、对象存储、检索服务；用临时目录和固定输入，把替身放在 I/O 边界。
- 不读 `.env`、不碰真实密钥与运行数据，也不把它们复制进夹具、日志或报告。
- 用户已有实现先保留：补表征测试，暴露缺陷再由测试驱动最小修复；不要为了制造 RED 去删代码。

## 边界

- 不引入新测试框架；确实需要时，先说明影响再动手。
- 改动外部接口、持久化格式、权限或安全行为前，先跟用户确认。
- 局部失败只重跑失败项和直接依赖，不把整个流程从头再来。
